# Runbook: OPNsense Tailscale subnet router

> Rewritten for OPNsense at the 2026-11-10 cutover; the subnet router was pfSense (Headscale node 10, `100.64.0.9`) before.

**What it is:** OPNsense (`10.0.20.1`, Proxmox VM 100) is a Tailscale subnet
router on the self-hosted Headscale tailnet. It is what lets Tailscale clients
reach the Sofia LAN, the mgmt and k8s VLANs, and the WireGuard-transited remote
sites. It also offers itself as an exit node.

**Design:** [`docs/plans/2026-08-03-pfsense-tailscale-subnet-router-design.md`](../plans/2026-08-03-pfsense-tailscale-subnet-router-design.md) (written for pfSense; the routes, ACLs and NAT carried over)

| Fact | Value |
|---|---|
| Tailnet address | `100.64.0.17` (Headscale node ID 399, name `opnsense`) |
| Tags | `tag:infra` (owned by `group:admin`), drives `autoApprovers` |
| Node expiry | None: disabled on 2026-11-10 with `headscale nodes expire -i 399 --disable`, as pfSense's node had. Without `--disable` that command expires the node at once |
| Advertised routes | `192.168.1.0/24`, `10.0.10.0/24`, `10.0.20.0/24`, `192.168.0.0/24`, `192.168.8.0/24`, `192.168.9.0/24`, `192.168.3.0/24` (Mladost 3, since 2026-10-03) + exit node |
| Client DNS for `.lan` | Technitium **`10.0.20.201`** (NOT `.200`, nothing listens there) |
| Plugin | `os-tailscale`; `tailscale0` is assigned as interface `opt5` (description `Tailscale`) |
| Settings source | `playbooks/files/opnsense/tailscale.yml`, applied by `playbooks/tasks/opnsense/tailscale.yml` (`--tags tailscale`) |
| Pre-auth key | Vault `secret/opnsense` `tailscale_preauth_key` (one-time) |
| Policy source of truth | `stacks/headscale/acl.hujson` (**git-crypt**, main checkout only) |
| Probe | CronJob `tailscale-subnet-router-probe`, `headscale` ns, every 6 h, pings `100.64.0.17` (`stacks/headscale/subnet-router-probe.tf`) |

## Re-run / repair

Always claim presence first: this mutates the estate's single point of failure.
Never change Tailscale settings in the OPNsense GUI; edit the YAML and run the
playbook.

```bash
cd ~/code/infra
presence claim host:opnsense --purpose "tailscale subnet router"

ansible-playbook -i playbooks/inventory.ini playbooks/opnsense.yml -e opnsense_allow_production=true --tags tailscale --check --diff   # dry run
ansible-playbook -i playbooks/inventory.ini playbooks/opnsense.yml -e opnsense_allow_production=true --tags tailscale                # apply
scripts/opnsense-verify --host 10.0.10.1 --profile production
```

The tasks write the plugin's authentication, routes and settings over the API
and call `tailscale/service/reconfigure` only when something changed, so a
healthy second run reports `changed=0`.

**Adding a route: three steps, or it silently carries nothing:**

1. `advertised_routes` in `playbooks/files/opnsense/tailscale.yml`, then run the
   playbook with `--tags tailscale`.
2. `autoApprovers.routes` in `stacks/headscale/acl.hujson`, then
   `cd stacks/headscale && ../../scripts/tg apply`; or approve the route on the
   node directly: `headscale nodes approve-routes -i 399 -r <routes>`.
3. Check the route shows as approved (`headscale nodes list-routes`, below). The
   OPNsense playbook does not check approval, and an advertised-but-unapproved
   route is served by nobody.

Tailnet traffic to a new LAN may also need the outbound NAT and filter rules
in `nat_outbound.yml` and `filter.yml` (the `100.64.0.0/10` entries, see
Health checks).

> `acl.hujson` is git-crypt encrypted. **Edit and apply it from the main checkout
> only**: a worktree bypasses the filter and Terraform would render ciphertext
> into the ConfigMap, breaking policy for every client.

## Health checks

```bash
# Headscale side: node online, tagged
kubectl -n headscale exec deploy/headscale -c headscale -- headscale nodes list | grep opnsense

# Routes approved (field is approved_routes; the table header "Approved" is not the JSON key)
kubectl -n headscale exec deploy/headscale -c headscale -- headscale nodes list-routes

# OPNsense side (root's shell is csh)
ssh root@10.0.10.1 'tailscale status; tailscale ip -4'
ssh root@10.0.10.1 'cat /etc/rc.conf.d/tailscaled'     # generated: what runs on every boot
ssh root@10.0.10.1 'pfctl -sn | grep 100.64'           # the two SNAT rules
ssh root@10.0.10.1 'pfctl -sr | grep tailscale0'       # the two tailnet filter rules

# Probe on demand (don't wait 6h)
kubectl -n headscale create job --from=cronjob/tailscale-subnet-router-probe probe-adhoc-$(date +%s)
kubectl -n headscale logs -l job-name=probe-adhoc-<ts> -c probe
# healthy: enrolled=1 router_up=1 sofia=1 k8s=1 success=1
```

`/etc/rc.conf.d/tailscaled` is generated by the plugin from `config.xml`
(`# DO NOT EDIT`). Its `tailscaled_up_args` line should carry
`--advertise-exit-node --accept-routes=false --accept-dns=false --ssh=false`,
`--login-server=https://headscale.viktorbarzin.me` and
`--advertise-routes=` with the seven routes above.

The SNAT rules, as seen on 2026-11-10:

```
nat on vtnet0 inet from 100.64.0.0/10 to any -> (vtnet0:0) port 1024:65535   # exit node to WAN
nat on wg0 inet from 100.64.0.0/10 to any -> (wg0:0) port 1024:65535         # tailnet to the WireGuard sites
```

The filter rules on `tailscale0` are `filter.yml`'s two `interface: Tailscale`
entries: tailnet to CCTV (`10.0.30.0/24`) blocked, tailnet to anything else
passed.

## Alerts

| Alert | Means | First move |
|---|---|---|
| `TailscaleSubnetRouterDown` | OPNsense did not answer a tailnet ping to `100.64.0.17` | `ssh root@10.0.10.1 'tailscale status'`; `configctl tailscale restart`; re-run the playbook with `--tags tailscale` |
| `TailscaleLanUnreachableViaTailnet` | Router answers, but a route carries no traffic | Check route approval; `pfctl -sn \| grep 100.64`; if `route="192.168.8.0/24"` or `.0.0/24`, check the WG leg (`wg show wg0`) |
| `TailscaleSubnetRouterProbeStale` | No probe result for >2 runs (13 h) | Reachability is **unverified, not necessarily broken**. Check the CronJob and whether the `tag:probe` key still exists |

Inhibited under `WANGatewayUnreachable`, `InternetEgressDown`, `HeadscaleDown`,
`EdgeFirewallVMDown` (the firewall VM stopped), and during
`NodeMaintenanceInProgress`.

## Diagnosis traps

Three ways to reach a confidently wrong conclusion here. All were hit while
building the pfSense router, and none depends on the firewall's OS.

1. **`tailscale nc` exits 0 without connecting.** It will happily report success
   while tcpdump shows no packets leaving the firewall. Prove a path by reading
   real payload back (an SSH banner, an HTTP status line), never by exit code.
2. **A cluster pod reaches the LAN without the tunnel.** `192.168.1.x` and
   `10.0.20.x` are reachable from pods over ordinary cluster routing, so testing
   from in-cluster proves nothing unless traffic is forced through tailscaled
   (the probe uses its outbound HTTP proxy) *and* you have confirmed a `100.x`
   address first.
3. **busybox `wget` resolves `localhost` to `::1`** while tailscaled's proxy
   listens on IPv4: "Connection refused" that looks exactly like a dead tunnel.
   Use `127.0.0.1`.

Also:

- **Filter rules need the `opt5` assignment.** On pfSense, rules bound to the
  `Tailscale` interface group never rendered (the group had no members) and
  traffic passed only because pf did not filter it. On OPNsense `tailscale0` is
  assigned as `opt5` (`misc.yml`), so the rules render;
  `pfctl -sr | grep tailscale0` should print two rules.
- **The pre-auth key sits in the config.** The plugin stores it in `config.xml`,
  so it is in the nightly `config.xml` copy under `/mnt/backup/opnsense/`, and
  writes it into `/etc/rc.conf.d/tailscaled`. It is passed to `tailscale up`
  only while the state file has no profile. Use one-time keys.
- **The first start after registration shows a login URL.** From the rebuild
  (`docs/runbooks/opnsense.md`, Rebuild step 7): the plugin passes the key only
  when a state file exists without a profile, so the first start shows a login
  URL; `configctl tailscale restart` then logs in.

## Re-registration

Follow `docs/runbooks/opnsense.md`, Rebuild step 7: create a one-time key
(`headscale preauthkeys create --user 1 --expiration 1h`), store it in Vault as
`secret/opnsense` `tailscale_preauth_key`, run the playbook with
`--tags tailscale`, then `configctl tailscale restart` if the first start shows a
login URL.

A new registration can get a new node ID and tailnet address. Afterwards tag
the node `tag:infra`, approve the seven routes and the exit node
(`headscale nodes approve-routes -i <id> -r <routes>`), and check that
`stacks/headscale/subnet-router-probe.tf` and the `TailscaleSubnetRouterDown`
summary still name the right address.

Open question: re-registering a box whose node was deleted in Headscale while
its local state still holds a profile is not tested on OPNsense; the plugin
skips the key in that case.

# Databases

Moved verbatim from the repo's agent instruction files (`AGENTS.md`, `.claude/CLAUDE.md`) on 2026-09-22, when the two merged into one root `AGENTS.md`. Related as-built docs: `docs/architecture/databases.md`.

## Database Host

**`postgresql_host`** in `config.tfvars` is `pg-cluster-rw.dbaas.svc.cluster.local`. Since the PG18 cutover on 2026-10-15 the active cluster is `pg-cluster-v18` (PG 18.6); `pg-cluster` is the read-only PG16 rollback copy, hibernated since 2026-10-19 (no pod, PVC `pg-cluster-1` kept). Both `pg-cluster-rw.dbaas.svc.cluster.local` (through a CoreDNS rewrite) and `postgresql.dbaas` reach the primary of the cluster named in `var.pg_active_cluster` in `stacks/dbaas`. Either name works for new work; for replica reads use `pg-cluster-v18-ro`. This variable is shared by ~12 stacks. Upgrade and rollback: `docs/runbooks/pg-cluster-major-upgrade.md`.

**pg-cluster-v18 since 2026-11-03**: 2 instances (was 3), new instances on `proxmox-lvm-encrypted-sas` (the SAS RAID1, where database engines live), `checkpoint_timeout=30min` (was 15; checkpoint page writes were most of the primary's write IOPS) and `wal_keep_size=2GB` (was 512MB). The third instance, `pg-cluster-v18-1`, had been stuck since ~2026-11-02 on an old timeline (it needed a WAL segment from timeline 4 that the primary had removed; there is no WAL archive) while CNPG kept reporting the cluster healthy, 3/3. `CNPGReplicaWalReceiverDown` now catches that state. On one host and one array a third copy only multiplied writes; the second instance is for second-scale switchovers during node reboots and drains, and CNPG cannot split-brain at 2 because the operator, not a quorum vote, decides the primary through the Kubernetes API.

**CNPG tuning** (in `stacks/dbaas/modules/dbaas/main.tf`): `shared_buffers=2048MB`, `effective_cache_size=3072MB`, `work_mem=16MB`, `max_connections=200`, pod memory **4Gi limit / 2816Mi request**. **shared_buffers went 1->2 GB on 2026-09-02 (infra#86) because the pool was fully subscribed by ONE tenant**: `dawarich` held 127,029 of 131,072 buffers (992 MB) with zero free, against `claude_memory`'s 2,290 — its `points` table is 3.5 GB with 4.7 billion buffer hits at a 96.6% hit rate, so a real working set rather than a runaway query. **A small tenant on a fully-subscribed pool cannot keep an index resident at all**: prewarming claude-memory's 4,456-page HNSW index left 1,095 pages (24%) by the time `pg_prewarm` returned and **0 within 60 s**. Check `pg_buffercache` grouped by `reldatabase` before attributing a slow query to anything else — and note this raised the odds rather than guaranteeing anything, since dawarich's working set exceeds 2 GB too. The request rose only to 2816Mi, not back to 3Gi+, because node2/node3 have 2.2-2.7 GiB of free REQUESTS while running at ~40% actual usage; the 2026-07-26 reduction for N-1 headroom is deliberate, so do not undo it wholesale. **Write-reduction (2026-06-29, code-oflt, analysis #6922):** `checkpoint_timeout=15min` + `max_wal_size=4GB` + `min_wal_size=1GB` (checkpoints were 100% timer-driven at the 5-min default, bursting FPIs onto sdc); `archive_timeout=0` (CNPG forces `archive_mode=on` but `.spec.backup` is empty → a 16MB WAL switch every 300s shipped nowhere = ~4.6 GB/day waste; daily `pg_dump` is the real backup); `commit_delay=2500`µs (group-commit fsync coalescing, safe for all DBs incl financial); `wal_compression=zstd` (was pglz). All reloadable (no restart). **`shared_preload_libraries: [pg_prewarm]` + `pg_prewarm.autoprewarm=on`/`autoprewarm_interval=300` (2026-09-02, infra#86)** — postmaster-level, so unlike everything above it costs ONE rolling restart to change (`unsupervised`/`restart`, replicas first); removing an entry later needs a full restart of every instance. It exists because **a NOVEL query, not an idle period, is what pays for a cold index**: measured on claude-memory's HNSW index, a repeated query read 0 blocks from disk at 0s/30s/60s/120s idle, while a query with a new embedding read 199-491 blocks off sdc at ~8.9ms each (1.25-2.48s) because only 339 of the index's 4,456 pages were ever resident. Postgres caches pages on demand, so a 35MB index in a 1GB `shared_buffers` is **not** implicitly resident — it is resident only where someone has already walked. `pg_prewarm` loads all of it (0 blocks, 0.27-0.49s afterwards) and autoprewarm makes that survive a restart. **Do not diagnose a slow first query as an eviction problem before checking `pg_buffercache` residency** — a decay measurement that varies its query text measures query-to-query path variance, not decay, and reads as noise. The same pattern has run on immich's own (separate, non-CNPG) Postgres since its `clip_index` work. **Reaching that Postgres: `homelab k8s db immich` does NOT go there.** It resolves to the shared CNPG, which still carries a legacy `immich` database holding the pre-v3 schema (`assets`, `users`, `exif`) with zero rows in every table, so queries answer `0` instead of erroring and read as "the library is empty" (measured 2026-09-12). Use `kubectl exec -n immich <immich-postgresql-pod> -- psql -U immich -d immich`. Immich v3 also renamed the tables: `asset`, `"user"` (quoted), `asset_exif`, `album`, `api_key`, and asset filtering moved from the `isVisible`/`isArchived` booleans to a `visibility` enum (`visibility = 'timeline'`). The stale shared-CNPG database is a drop candidate, same class as bead code-lile. **Apply gotcha:** the Cluster is a `null_resource.pg_cluster` + local-exec `kubectl apply` — bump its `pg_params` trigger or the YAML edit is inert, and apply with `-target=module.dbaas.null_resource.pg_cluster` for fast iteration. (The `mysql_standalone` VCT-annotation drift that used to error broad `dbaas` applies was **fixed 2026-06-30** — `ignore_changes` on the STS `volume_claim_template`, since pvc-autoresizer owns PVC sizing and the VCT is immutable post-creation anyway.)

## Cloud on the shared CNPG cluster

Cloud (Forgejo `viktor/cloud`, plan `docs/plans/2026-11-12-cloud-v1-and-operator.md` there) creates one Postgres role and database per Project on `pg-cluster-v18`. This repo owns only the fixed pieces, in `stacks/dbaas/modules/dbaas/cloud_postgres.tf` and `cloud_postgres_rules.tf`; Project roles and databases belong to Cloud's database (AGENTS.md, "Cloud-owned objects").

| Piece | What it is |
|---|---|
| `cloud_projects` | NOLOGIN group. Every Project role is a member. It holds grants only; pg_hba matches Project roles by name |
| `cloud_provisioner` | LOGIN, CREATEDB, CREATEROLE, CONNECTION LIMIT 5, ADMIN OPTION (not INHERIT or SET) on `cloud_projects`, SET on parameter `temp_file_limit`, `search_path = pg_catalog, pg_temp` as a role setting. Created with `PASSWORD NULL`; Vault static role `pg-cloud-provisioner` sets the password |
| `cloud_state` | LOGIN, CONNECTION LIMIT 10, created with `PASSWORD NULL`, owns database `cloud_state` (the reconciler's OpenTofu state, one schema per Project). CONNECT revoked from PUBLIC. Vault static role `pg-cloud-state`. No grant on `terraform_state` |
| `cloud` | Cloud's console database, a normal `app_databases` entry with Vault role `pg-cloud` |

**PG 16+ CREATEROLE (live: 18.6).** `cloud_provisioner` can alter, drop and grant only roles it holds ADMIN OPTION on: the ones it created, plus `cloud_projects`. It cannot change any existing app's role or password, drop its database, or create SUPERUSER, REPLICATION or BYPASSRLS roles. To create a database owned by a Project role it first grants itself SET on that role (`GRANT p_x TO cloud_provisioner WITH SET TRUE`). `tests/cloud-postgres.test.sh` checks all of this on PostgreSQL 18.6. ADMIN OPTION on `cloud_projects` lets it add any existing role, `postgres` included, to the group. That changes nothing, because pg_hba matches Project roles by name and the group carries no network rule.

**pg_hba.** `.spec.postgresql.pg_hba` on `pg-cluster-v18` carries seven rules, which CNPG places after its fixed rules and before `host all all all scram-sha-256`. The first match wins:

```
host postgres cloud_provisioner all scram-sha-256
host "/^p_[a-z0-9_]+$" cloud_provisioner all scram-sha-256   # Project databases
host all cloud_provisioner all reject
host cloud_state cloud_state all scram-sha-256
host all cloud_state all reject
host sameuser "/^p_[a-z0-9_]+$" all scram-sha-256           # a Project role reaches only its own database
host all "/^p_" all reject
```

Project roles are matched by name (PG 16+ regex), not by membership of `cloud_projects`, so a grant of that group cannot change any role's access. **The reconciler must name every Project role and database `p_<name>`, create each role `IN ROLE cloud_projects`, and refuse a name that matches an existing role or database.** pg_hba cannot enforce that: a role it created under another name falls through to `host all all all` and can connect to any database that grants CONNECT to PUBLIC. **Audit:** the CNPG exporter on the primary runs `local.cloud_provisioner_audit_sql` (`cloud_postgres_rules.tf`, through the `pg-custom-queries` ConfigMap) and exports `cnpg_cloud_provisioner_foreign_roles_count`, the number of roles `cloud_provisioner` administers, directly or through a role it administers, whose name does not match `^p_[a-z0-9_]+$` (`cloud_projects` excluded). Alert `CloudProvisionerForeignRole` (critical, `notify: page`) fires above 0 for 2m; its summary holds the query that lists the roles. Postgres records the creator of a role as holding ADMIN OPTION on it, granted by the bootstrap superuser, so `cloud_provisioner` cannot revoke that record to hide a role; `tests/cloud-postgres.test.sh` checks that, a rename away from `p_`, and a role made by a `p_*` role it gave CREATEROLE. On 2026-11-13 that includes `crowdsec_metabase`, `dawarich_queue` and `prowlarr_log`, which have no role of their own name. No live role or database name started with `p_` and no `cloud*` role existed, so no existing app changes. CNPG reloads Postgres on a `pg_hba` change; nothing restarts. The rules reach the cluster through `null_resource.pg_cluster_v18`, whose `pg_hba` trigger reruns its `kubectl apply`. A server-side dry run on 2026-11-13 showed that apply adds only `pg_hba` to the live Cluster. **`pg-cluster`, the PG16 rollback copy, does not carry these rules.** A rollback to it must add them before Cloud's roles move with it.

**Connection ceiling: 20.** The reconciler keeps the sum of the CONNECTION LIMITs of all Project roles at or below 20 (`POSTGRES_CONNECTION_CEILING` in Cloud's instance config), and refuses a Project change that would exceed it. Each Postgres Service's role gets the CONNECTION LIMIT of its Size: nano 2, small 4, medium 8 (the cloud repo's `drizzle/0010`). Postgres cannot enforce a total across roles, so the reconciler enforces it and an audit detects when it does not hold. **Audit:** the CNPG exporter on the primary runs `local.cloud_role_limits_audit_sql` (`cloud_postgres_rules.tf`, query `cloud_provisioner_role_limits` in `pg-custom-queries`) over the LOGIN roles `cloud_provisioner` administers and exports `cnpg_cloud_provisioner_role_limits_unlimited` (roles with CONNECTION LIMIT -1 or above 8, the medium Size) and `cnpg_cloud_provisioner_role_limits_connlimit_sum` (their limits added up, -1 counted as 0). Alerts `CloudProjectRoleUnlimited` (above 0 for 2m) and `CloudProjectConnectionsOverCeiling` (sum above 20 for 5m) are critical and page. Without them a stolen `pg-cloud-provisioner` credential could create a `p_` role with no limit and use up the cluster's connection slots unnoticed; the alerts detect it, they do not stop it. `tests/cloud-postgres.test.sh` covers -1, 9, 8, a sum of 21 and a role the provisioner does not administer. The arithmetic, at full Cloud load:

| | Connections |
|---|---|
| `max_connections` 200 minus `superuser_reserved_connections` 3 | 197 |
| Peak client backends on the primary, 2026-11-06 to 11-13 (`max_over_time(sum(cnpg_backends_total{pod=~"pg-cluster-v18-.*"})[7d:1m])`; median over the cluster's 12 days of history: 111) | -150 |
| `cloud_provisioner` 5 + `cloud_state` 10 | -15 |
| Role `cloud`: console pool 4 + LISTEN 1, reconciler pool 4, `migrate` 1 (`docs/architecture/cloud.md`) | -10 |
| Left for Project roles | 22 |
| **Project ceiling** | **20**, leaving 2 spare at the peak |

**`cloud_provisioner` budget: 5.** Its CONNECTION LIMIT 5 is shared by everything the reconciler (one replica) does as that role, so Cloud caps each user (the cloud repo's `docs/build/m2-contract-rendered.md`, "Postgres"): OpenTofu runs plan and apply with `-parallelism=2` and its postgresql provider with `max_connections = 3` per database pool, so at most 4 (two operations hold at most 2 each). A pool of 2 deadlocks when two databases are created or dropped at once: each holds a lock transaction from the pool, waits on `pg_advisory_xact_lock`, and then needs a second pooled connection; the database-size loop holds 1; the `temp_file_limit` step holds 1 only after OpenTofu exits. Peak 5. Past it Postgres answers `too many connections for role "cloud_provisioner"` and the apply fails. A second reconciler replica, or a higher parallelism, needs a higher limit here first.

To give Projects more, raise `max_connections` together with the primary's memory (Viktor's call), or put Project roles behind a pooler. Re-measure the peak over at least a week before changing the number.

**Project disk use: measured now, enforced in M5.** Every Project database shares the primary's data volume with every homelab app database: 40 GiB, 23 GiB used and 17 GiB free on `pg-cluster-v18-2` on 2026-11-13, annotated for pvc-autoresizer (grow 20% when under 10% free, up to 100 GiB). Postgres has no per-database quota and `temp_file_limit` covers only temp files, so until M5 a User with their Project's credentials can INSERT until the volume is full, and then writes stop for every app on the cluster. The decision (M2 contract point 5): Cloud's reconciler measures `pg_database_size` of each Cloud database every 300 s as `cloud_provisioner` and exports `cloud_postgres_database_bytes{project,service}` and `cloud_postgres_database_limit_bytes{project,service}` (the Size's disk); Cloud alerts at `cloud_postgres_database_bytes / cloud_postgres_database_limit_bytes > 0.8`, a rule M4 adds with Cloud's stack; M5 enforces the limit. Until then `PVPredictedFull` warns about the volume as a whole and names no database. The worker also sets `temp_file_limit` on each Project role to its Size's disk in kB.

**`cloud_provisioner` runs inside databases that Project roles own.** The reconciler's `postgresql_grant` resources connect into each Project database as `cloud_provisioner`, and provider 1.27.0 runs unqualified `pg_advisory_xact_lock`, `pg_roles` and `pg_database` there. The owner of that database can `ALTER DATABASE <own> SET search_path = public, pg_catalog` and create `public.pg_advisory_xact_lock(bigint)`, which would then run with `cloud_provisioner`'s rights and could reset any other `p_*` role's password. The role setting `search_path = pg_catalog, pg_temp` outranks the database setting, and only the superuser can set a per-database value for `cloud_provisioner`, so the planted function is never found. `tests/cloud-postgres.test.sh` plants this trap, shows it works on a role without the setting, and checks that no other role changes. Any other role that ever connects into a `p_*` database needs the same setting.

**Per-Project limits.** `temp_file_limit` is superuser-only, so `cloud_provisioner` sets it on Project roles through its SET grant, and a Project role cannot lift it. `statement_timeout` and `idle_in_transaction_session_timeout` can be set per role too, but any role can change them in its own session, so for a Project they are defaults, not limits.

## MySQL

One MySQL server serves every MySQL tenant (20 schemas on 2026-10-19, among them nextcloud, forgejo, grafana, uptimekuma, wrongmove, phpipam, roundcubemail and technitium). It is a plain StatefulSet in `stacks/dbaas/modules/dbaas/main.tf`, not an operator or a Helm chart.

| Piece | Value |
|---|---|
| Active instance | StatefulSet `mysql-v26`, `docker.io/library/mysql:26.10.0`, PVC `data-mysql-v26-0` (30Gi, `proxmox-lvm-encrypted-sas`), config map `mysql-v26-cnf` |
| Host for apps | `mysql.dbaas.svc.cluster.local:3306` (`var.mysql_host`). The `mysql` Service selects the instance named in `local.mysql_active` |
| Rollback copy | StatefulSet `mysql-standalone`, `mysql:8.4.8`, at 0 replicas since 2026-10-19. Its PVC `data-mysql-standalone-0` is kept and holds the data as of the 2026-10-15 23:11 UTC cutover, with `super_read_only` persisted in the datadir. Renovate holds its image pin |
| Users | the `mysql_static_user`, `mysql_exporter_user` and `mysql_verify_probe_user` provisioners exec into `<local.mysql_active>-0`; Vault's database engine rotates the rest |
| Backups | `mysql-backup` (00:30 UTC: users and grants to `grants_<ts>.sql.gz`, then one `mysqldump --single-transaction --routines --events` per database; it replaced the full `--all-databases` dump plus the separate `mysql-backup-per-db` job on 2026-11-03) on the 26.10.0 client, to `/srv/nfs/mysql-backup` on 192.168.1.127 (PVC `dbaas-mysql-backup-host`), 14-day retention. `mysqldump` rounds FLOAT columns to about 6 significant digits; DOUBLE and DECIMAL are exact |
| Monitoring | `mysqld-exporter` connects through the `mysql` Service. `MysqlStandaloneDown` and `MySQLNotServing` watch `mysql-v26` (the first alert keeps its old name) |
| Health script | `.claude/scripts/db-health.sh` checks that `mysql-v26-0` is ready and writable, and its connection count |

To bring the rollback copy back, set `replicas = 1` on `kubernetes_stateful_set_v1.mysql_standalone` and apply `dbaas`; the pod reattaches `data-mysql-standalone-0` and starts read-only. Major upgrades and the full rollback: `docs/runbooks/mysql-major-upgrade.md`. Restores: `docs/runbooks/restore-mysql.md`.

## Redis Service Naming (read before wiring a new consumer)

The Redis stack (`stacks/redis/`) exposes three distinct entry points. Pick the one that matches the client's connection pattern — the wrong one causes READONLY errors or silent connection drops.

| Endpoint | Port(s) | Use for | Backed by |
|----------|---------|---------|-----------|
| `redis-master.redis.svc.cluster.local` | 6379 (redis), 26379 (sentinel) | **Default for new services.** Write-safe — HAProxy health-checks nodes and routes only to the current master. Matches `var.redis_host`. | `kubernetes_service.redis_master` → HAProxy → Bitnami StatefulSet |
| `redis-node-{0,1,2}.redis-headless.redis.svc.cluster.local` | 26379 | **Long-lived connections (PUBSUB, BLPOP, MONITOR, Sidekiq).** Use a sentinel-aware client with master name `mymaster`. Example: `stacks/nextcloud/chart_values.yaml:32-54`. | Bitnami-created headless service → pod DNS |
| `redis.redis.svc.cluster.local` | 6379 | **Do NOT use.** Helm chart's default service — selector patched by `null_resource.patch_redis_service` to match `redis-haproxy`, so today it behaves like `redis-master`. This patch is load-bearing but temporary; consumers hard-coded on this name are tracked in a beads follow-up (T0). | Bitnami chart (patched) |

**HAProxy's `timeout client 30s` closes idle raw Redis connections** — any client that holds a connection open for pub/sub, blocking commands, or replication streams MUST use the sentinel path. Uptime Kuma's Redis monitor hit this limit and had to be re-pointed at the sentinel endpoint (see memory id=748).

**When onboarding a new service:** start from `redis-master.redis.svc.cluster.local:6379` via `var.redis_host`. Only reach for sentinel discovery if the client library supports it natively (ioredis, redis-py Sentinel, go-redis FailoverClient, Sidekiq `sentinels` array) AND the workload uses long-lived connections.

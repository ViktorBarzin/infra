# Known issues

Moved verbatim from the repo's agent instruction files (`AGENTS.md`, `.claude/CLAUDE.md`) on 2026-09-22, when the two merged into one root `AGENTS.md`. Related as-built docs: `docs/known-issues.md`.

## Known Issues
- **A Kubernetes upgrade erases the kubelet post-join tune on every node** (found 2026-08-16; **the mechanism is fixed as of 2026-09-03, the reservations are still absent**; **survives upgrades as of 2026-10-01**, see the end of this entry). `kubeadm upgrade node` rewrites `/var/lib/kubelet/config.yaml` from the cluster-wide `kube-system/kubelet-config` ConfigMap, which does **not** carry this homelab's extra keys, so the v1.35.7 upgrade on **2026-07-26/27** wiped them from all six nodes (config mtimes 23:57→02:39, a rolling per-node sequence). Nothing alerted, and the first visible symptom arrived weeks later looking unrelated: the proxy VPN gateway could not start (`SysctlForbidden`, `net.ipv4.ip_forward` gone from `allowedUnsafeSysctls`), and a remote browser spent four days reconnecting to a Service with no endpoints. **THE CAUSE WAS A ONE-SHOT WITH NO RECONCILER**: `modules/create-template-vm/k8s-node-post-join-tune.sh` ran once as a cloud-init runcmd after `kubeadm join` and nothing re-applied it. That script is **deleted** (2026-09-03) and `playbooks/k8s-node-tuning.yml` owns those settings now. **It is NOT reconciled automatically, and for two days five documents said it was** — this bullet, `CONTEXT.md`, `docs/architecture/{security,networking}.md` and two others all claimed "reconciled hourly" while no timer, cron entry or CronJob anywhere ran it (checked 2026-09-05, code-yypr). What runs hourly as of 2026-09-05 is a **drift CHECK**: `scripts/k8s-node-drift-check` on the devvm (`k8s-node-drift-check.timer`, installed by `playbooks/devvm.yml`) runs `ansible-playbook --check --diff` plus `scripts/check-node-kubelet-tune`, pushes gauges to the pushgateway, and five rules in the monitoring stack (`K8sNodeConfigDrift`, `K8sNodeKubeletTuneDrift`, `K8sNodeDriftCheckStale`, `K8sNodeDriftCheckNeverRun`, `K8sNodeDriftCheckFailing`) put a warning in Slack `#alerts` via Alertmanager. **Re-applying is still a human running the playbook**, deliberately: an invalid combination of kubelet keys makes kubelet exit at boot with console-only recovery, which is not a thing to do unattended. The freshness of the metric is alerted on too, so a checker that quietly stops is itself the signal. **Now written by the playbook**: `shutdownGracePeriodByPodPriority` (the priority-ordered graceful-shutdown work, bead `code-xgcg`), `memorySwap: LimitedSwap`, `serializeImagePulls`, a finite `imageMaximumGCAge`, containerd `discard_unpacked_layers`, `allowedUnsafeSysctls`, plus `pigz`. **Also now written by the playbook** (2026-09-05, code-yypr, at the kubelet's own default values so behaviour is unchanged): `imageGCHighThresholdPercent`/`imageGCLowThresholdPercent` 85/80 and the full `evictionHard` set. **Still deliberately absent**: `systemReserved`, `kubeReserved` and `evictionSoft` — bead `code-eu6l`, not an oversight. The two reservations carve **1,024 MiB** (512 + 512), not the ~1,424 MiB this bullet used to say; that older figure also counted moving `evictionHard.memory.available` from 100Mi to 500Mi, which the playbook explicitly declines to do. Headroom moved too: after the 2026-09-04 rightsizing pass every untainted node stays positive after the carve-out, k8s-node4 lowest at 2,188 MiB, so code-eu6l is ready to be re-taken on capacity rather than deferred by it. `maxParallelImagePulls` is also skipped on purpose (an aggregate ceiling containerd's own streams already reach). **Detect drift with `scripts/check-node-kubelet-tune`** (reads each kubelet's live `/configz`, not the file on disk; exit 1 = drift, 2 = unreachable). **The trap that outlived the fix**: node1 carries `/etc/containerd/conf.d/99-nvidia.toml`, a whole-config snapshot the nvidia toolkit takes from `containerd config dump`, and containerd merges imports last-wins per key — so a drop-in silently overrides the root config. It was found pinning `discard_unpacked_layers` (2026-09-02), then `sandbox_image` AND `max_concurrent_downloads` (2026-09-03, only revealed by restarting containerd and re-reading the dump). **Any containerd setting added to that playbook must also be added to its `containerd_dropin_overrides` list, or node1 quietly will not have it**, and the merged-config assert must check every one of them. Note the drop-in spells the pause key `sandbox_image` (the v2 CRI name) while a v3/v4 root spells it `sandbox` under `pinned_images`. **It recurred, and the durable fix is now built (2026-10-01).** The v1.35.9 upgrade on 2026-09-27/28 erased the tune from all six nodes again (`scripts/check-node-kubelet-tune`: allowedUnsafeSysctls, imageMaximumGCAge, memorySwap and shutdownGracePeriodByPodPriority missing everywhere), and the proxy VPN gateway was down for three days with 26 pods rejected as `SysctlForbidden` filling the `proxy` namespace pod quota. The playbook was re-applied, kubelet restarted on each node and the failed pods cleared. `stacks/rbac/modules/rbac/kubelet-config-tuning.tf` now merges the playbook's kubelet keys into `kube-system/kubelet-config`, so `kubeadm upgrade node` and `kubeadm join` write them themselves. The playbook still owns the node-level half (logind, containerd, host sysctls) and remains what the drift check compares against, so the two must change together.

- **Controllers restart with "leader election lost" whenever etcd is slow** (measured 2026-10-19). etcd is a single member whose WAL shares the pve HDD `sdc` with every VM disk, so its fsync p99 crosses 1 s in about 5% of 2-minute windows and reaches 3-8 s during heavy IO (image pulls, node upgrades or reboots, the weekly fstrim on k8s-master until 2026-10-19). Any controller on the client-go defaults (lease 15 s, renew deadline 10 s, request timeout 5 s) loses its Lease in those seconds and exits, so they restart together: in the 3 days to 2026-10-19, kyverno 142, pvc-autoresizer 73, tigera-operator 64, gpu-operator 62, nfs-csi sidecars 45-48, proxmox-csi sidecars 38-39. The same windows produce `context deadline exceeded` on `10.96.0.1:443` from every CNPG instance at about the same rate on node2, node3 and node4 (363-437 per pod per 24 h), so these are apiserver/etcd latency, not a per-node network path. Tuned to a 45 s renew deadline: kube-controller-manager and kube-scheduler (`stacks/rbac/modules/rbac/leader-election-tuning.tf`), the CNPG operator (`stacks/cnpg`), the proxmox-csi attacher, provisioner and resizer (`stacks/proxmox-csi`, 60 s/45 s/15 s), kyverno admission, background and cleanup (`stacks/kyverno`, `--leaderElectionRetryPeriod=9s`, which kyverno multiplies into 54 s/45 s/9 s) and the gpu-operator (`stacks/nvidia`, `operator.leaderElection.renewDeadline`). Not tunable through their charts today: pvc-autoresizer 0.21 has no leader-election flags at all; the tigera-operator binary has `-leader-election-lease-duration`, `-renew-deadline` and `-retry-period`, but chart v3.33.0 hardcodes the container args; csi-driver-nfs chart 4.13.5 hardcodes its sidecar args. Those three need a Helm post-renderer or an upstream chart change. A restart of these controllers is a few seconds of lost reconciliation and does not affect running workloads.
- **A Postgres write freeze can break Woodpecker's Forgejo login and stop every infra CI pipeline** (infra#116, 2026-10-15). Forgejo issues 1-hour OAuth access tokens and **rotates the refresh token on every use**. It tracks this as `oauth2_grant.counter` in the Forgejo MySQL DB, and every refresh token JWT carries the counter it was issued at (`cnt`). During the pg-cluster PG16→18 cutover the Woodpecker DB was read-only (`default_transaction_read_only`). Woodpecker refreshed viktor's token: Forgejo accepted it and bumped the counter, but Woodpecker failed to save the new pair (`fail to save user to store after refresh oauth token ... read-only transaction`). From then on every refresh failed with `oauth2: "unauthorized_client" "token was already used"`, and every pipeline on repo 82 ended in `error` with `could not load config from forge: ... token is expired`. **Recovery without a browser login**: decode the payload of `users.refresh_token` for viktor (Woodpecker DB, `users.id=2`) to read its `cnt`. Then, in the Forgejo DB, `UPDATE oauth2_grant SET counter=<cnt> WHERE id=1 AND counter=<cnt+1>` (grant 1 = user 1, app "Woodpecker CI"). Woodpecker's next refresh succeeds and `users.expiry` moves forward. Re-run the pipelines that errored, and check that the stacks they touched were applied: a restarted older pipeline gets cancelled by a newer one. The fallback is a fresh viktor login in the Woodpecker UI through Forgejo. **Prevention**: keep DB write freezes shorter than the time left on viktor's token (`users.expiry`), or recover as above straight after the freeze.
- **nvidia-namespace pods can't resolve cluster DNS** (found 2026-07-06): `getaddrinfo` fails for `kubernetes.default.svc` AND `*.svc.cluster.local` from *every* nvidia pod, despite a correct `/etc/resolv.conf` (nameserver `10.96.0.10`, ndots:2), a TCP-reachable kube-dns, and **no** NetworkPolicy in `nvidia` / no applicable Calico GNP (the only GNP `wave1-egress-observe-tier34` selects tier 3-edge/4-aux + is log-only; nvidia is tier `2-gpu`). UDP-53 to the kube-dns ClusterIP appears dropped while TCP:53 connects; **root cause not found**. Workaround: nvidia pods reach services **by IP** — `KUBERNETES_SERVICE_HOST` for the apiserver, a TF-interpolated Service ClusterIP otherwise (the gpu-vram-watchdog was migrated to this). Re-investigate if other nvidia-ns pods start needing DNS.
- **Kubernetes egress NetworkPolicies do nothing in tier 3-edge/4-aux namespaces** (found 2026-09-28): the Calico GNP `wave1-egress-observe-tier34` (`stacks/calico`, order 2000, `action: Allow` for all egress) selects those namespaces. Kubernetes policies sit at order 1000 in the same tier and only add allows, so traffic they don't match falls through to the GNP's allow-all instead of being dropped. Seen on the bastion: with only a Kubernetes egress policy, the pod reached 1.1.1.1:443. To restrict egress there, use a Calico `projectcalico.org/v3` NetworkPolicy with order < 2000 ending in `action: Deny` (example: `kubectl_manifest.egress` in `stacks/bastion/main.tf`). Ingress policies are unaffected, since the GNP covers Egress only. As of that date, bastion was the only tier-3/4 namespace with an egress policy.
- **CrowdSec Helm upgrade times out**: `terragrunt apply` on platform stack causes CrowdSec Helm release to get stuck in `pending-upgrade`. Workaround: `helm rollback crowdsec <rev> -n crowdsec`. Root cause found 2026-10-13: the chart hardcodes a 50Mi memory limit on the `wait-for-lapi-and-register` init container, which runs `cscli` (a 110 MB binary). At that limit the container thrashes on page cache in D state and never finishes, so new agent/appsec pods sit in `Init:0/1` until the Helm wait times out. Fixed by the `crowdsec-register-init-memory` Kyverno MutatingPolicy (`stacks/kyverno/modules/kyverno/crowdsec-agent-register.tf`), which raises it to 256Mi. **Now auto-healed** by the `helm-unstick` CronJob (see Monitoring → "Helm `pending-upgrade` auto-heal"): a wedged crowdsec/monitoring/nextcloud release is cleared within ~15m (delete-pending-secret, non-disruptive) without manual rollback.
- **OpenClaw config is writable**: OpenClaw writes to `openclaw.json` at runtime (doctor --fix, plugin auto-enable). Never use subPath ConfigMap mounts for it — use an init container to copy into a writable volume. Needs 2Gi memory + `NODE_OPTIONS=--max-old-space-size=1536`. **`mcp.servers` baked into the ConfigMap-loaded openclaw.json gets stripped by `doctor --fix`** — register MCP servers via `openclaw mcp set <name> <json>` in the container startup command instead (CLI-written entries persist across doctor runs). Current servers wired this way: `ha`, `context7`, `playwright` (sidecar at `localhost:3000/mcp`).
- **OpenClaw memory-core indexes `/workspace/memory/`, not `/home/node/.openclaw/memory/`**: `/home/node/.openclaw/memory/main.sqlite` is the index store, NOT a content source. Files written under `/home/node/.openclaw/memory/projects/<x>/*.md` will NOT be indexed. To populate memory-core, write Markdown under `/workspace/memory/projects/<source>/` and run `openclaw memory index --force`. This is what the daily `memory-sync` CronJob in `stacks/openclaw/` does for claude-memory → OpenClaw sync.
- **(Obsolete 2026-06-12) Goldilocks VPA**: VPA/Goldilocks was uninstalled (etcd-load-reduction); the old "Goldilocks may have added a limit that blocks the change" gotcha no longer applies. Use `krr` for right-sizing.

Tier 0/1/2 deferred. **The internal (ns-to-ns) half of each allowlist now derives faster from the east-west flow trail** (below): `SELECT DISTINCT dst_ns FROM edge WHERE src_ns='<ns>' AND action='allow'`. **External egress IS in that table since 2026-09-01** (`WHERE dst_type='network'` gives the internet destinations with their ports) — it used to be deleted, not merely absent, so the Calico flow-log W1.6 snapshot is no longer the only source. What the table still cannot give is the peer ADDRESS: Goldmane's proto carries no IP field at all, so a CIDR-scoped egress rule still needs the flow-log snapshot or netflow. Enforce-flips remain out of scope of the trail (observe-and-derive only; beads `code-8ywc`).
- **East-west flow trail (who-talks-to-whom, ADR-0014)**: Calico **Goldmane** (`goldmane.calico-system:7443`, gRPC/mTLS, ~60-min in-memory ring buffer — no etcd writes) + **Whisker** live UI (`whisker.viktorbarzin.me`, Authentik-gated) → **`goldmane-edge-aggregator`** streams Goldmane's `Flows.Stream` over mTLS and upserts the per-workload **edge set** into **CNPG DB `goldmane_edges`** (`edge`: src/dst namespace + workload + endpoint type, dst service + namespace, dst port, action, first/last seen, flow count — **widened 2026-09-01**, design `docs/plans/2026-09-01-service-identity-and-request-attribution-design.md` step 2; before that it was `(src_ns,dst_ns,action)` alone). **Aggregation is per WORKLOAD, not per pod** — Goldmane's endpoint name is the generated pod-set name (`traefik-7cbc567497-*`), so it is reduced to the stable workload (`traefik`) or a redeploy would add a row per rollout and a CronJob a row per tick; Whisker serves live per-pod detail. **The old `src_ns == dst_ns` drop rule also DELETED any flow with a non-workload end at BOTH ends** — Goldmane writes the literal `-` for such an end, so `('-','-')` matched the self-edge test. The test is now on endpoint TYPE (`workload`/`host`/`networkset`/`network`/`unknown`), so a genuine self-edge is still dropped while node and internet flows are kept and labelled. **But measure before repeating the design's framing: that deleted class is EMPTY today** — 0 of 2,168 live flows had `-` at both ends (2026-09-01), because **no Calico HostEndpoints are defined** (`kubectl get hostendpoints` → none) so Goldmane never types an end as `host`. The type test guards a class that appears the moment HostEndpoints exist; the immediate gain is the one-dash class, **1,116 of 2,168 flows (51%)**, which was kept all along but recorded as a bare namespace pair (`keel → -`) with no port, workload or type. Still dropped, now counted by reason in the aggregate log line: `intra-namespace` (both ends workloads in one namespace, the class awaiting a keep/drop decision) and `non-workload` (an end with no identity at all). **`homelab edges` output is unchanged** — it groups back up to `(src_ns,dst_ns,action)`; per-workload/port detail needs SQL or the coming Grafana dashboard. **Rows written before the widening are kept** with `-`/`unknown`/`0` sentinels, so a query on the new columns should add `src_type <> 'unknown'`; and because the identity tuple is wider, the FIRST digest after the deploy reports the whole re-observed graph once → daily **`goldmane-edges-digest`** CronJob posts first-seen edges to `#alerts` (consolidated to `#alerts`; the `#security` channel was abandoned 2026-06-25 — the shared webhook's Slack app isn't a member of it, so a `#security` override 404s; see runbook). **CERT-REUSE GOTCHA**: the aggregator's mTLS client cert reuses the operator's Tigera-CA-signed `whisker-backend-key-pair` Secret (Goldmane verifies CA-chain only) — **re-apply `stacks/goldmane-edge-aggregator` if the operator rotates it** (symptom: no `last_seen` updates, `AggregatorDown`). Service identity = namespace, + `service-identity` label only in `monitoring`/`kube-system`/`dbaas`. Health: `AggregatorDown` + `DigestFailing` alerts + cluster-health #48. **WHISKER-WEDGE GOTCHA** (2026-06-28): the operator's `whisker` NetworkPolicy allows DNS egress only to kube-dns *pods*, but whisker-backend resolves goldmane via the kube-dns *ClusterIP* — Calico drops UDP DNS to a ClusterIP under a podSelector-only egress rule, so when whisker-backend's gRPC stream breaks and it re-resolves, it wedges and the UI goes **empty** (the aggregator, a separate pod, is unaffected). FIX = additive egress NP `whisker-allow-dns-clusterip` (`stacks/calico`, allows whisker→10.96.0.10/32:53); the `whisker-watchdog` CronJob is a backstop. Manual heal `kubectl -n calico-system delete pod -l k8s-app=whisker`. Runbook: `docs/runbooks/goldmane-flow-trail.md`. (Goldmane is OSS tech-preview — reversible operator-CR toggle in `stacks/calico/main.tf`.)
- **Who reached the kube-apiserver (design step 4, 2026-09-01)**: the apiserver already carries `--authentication-config=/etc/kubernetes/pki/auth-config.yaml` with the `kubernetes` + `k8s-dashboard` OIDC issuers, Terraform-owned in `stacks/rbac/modules/rbac/apiserver-oidc.tf` over SSH and **byte-identical to the node** (sha256 `bdefc260…97e16`, cross-checked against the apiserver's own `apiserver_authentication_config_controller_last_config_info{hash}` metric — that metric is the fastest way to confirm which config is live, and the file is hot-reloaded, so an issuer change needs NO restart and NO manifest edit). There are **no `--oidc-*` flags and none wanted** (legacy flags allow one issuer). Measured: **zero** OIDC-authenticated audit events in 24h, while the shared kubeadm admin cert (`kubernetes-admin`, `credential-id X509SHA256=7a03b1f4…0616`, expires 2027-04-17) produced 116 mutating events in 1h — every human, agent and cron job on the devvm shares it, so the audit log cannot tell them apart. Landed inert: a `kubernetes-agent` Authentik app (`stacks/rbac/authentik-kubernetes.tf`), a **third issuer prefixing username AND groups with `agent:`** behind `var.agent_oidc_enabled` (**default false — with it off the rendered config is byte-identical, so the null_resource trigger does not move and an apply cannot touch the control plane**; flipping it needs a LOCAL apply with `TF_VAR_ssh_private_key` + `-replace`, because CI has no SSH key), and group-keyed ClusterRoleBindings (`oidc-group-bindings.tf`) for `kubernetes-*` and `agent:kubernetes-*`. The prefix is load-bearing: the audit event records `user.username`/`user.groups` and NOT the issuer, so a second client on one issuer would stay indistinguishable, and the prefix also means an agent inherits no human binding (agents are bound read-only). Verify with `kubectl --context agent@homelab auth whoami`. Break-glass stays the shared cert (authenticates via `--client-ca-file`, so an Authentik outage cannot block it) — note `scripts/t3-provision-users.sh` reads that same kubeconfig as `ADMIN_KUBECONFIG`, so retiring it is a provisioning change too. Runbook `docs/runbooks/apiserver-oidc-agent-identity.md`.
- **NO Kubernetes read is audited anywhere, and TWO audit policies exist with only one live (2026-09-01)**: the apiserver reads `/etc/kubernetes/audit-policy.yaml` (hand-deployed from `scripts/k8s-apiserver-audit-policy.yaml`, whose rule 1 is `level: None` on `get,list,watch`), while `stacks/rbac/modules/rbac/audit-policy.tf` writes a DIFFERENT policy to `/etc/kubernetes/policies/audit-policy.yaml` that nothing reads — its rules WOULD have logged reads. The log path and rotation flags disagree too. **Left inert on purpose**: its `triggers` are content hashes, so changing them re-runs an SSH provisioner that rewrites the apiserver manifest and restarts the API on the single control-plane node, and CI applies that stack with no SSH key. Measured 6h: 74,060 audit events (update 40,353 / create 21,368 / delete 10,082 / patch 2,257), **zero reads**, against 366,219 read requests served. Auditing Secret reads would cost ~+147 MB/day (+36% audit volume, **+4.2%** of Loki's 3.54 GB/day) and lands on apiserver disk + Loki, **never etcd** (etcd is not even scraped). Also corrected: on-node audit history is **~2.8 days, not 30** — `maxsize=100`/`maxbackup=10` rotates every 6-7h at ~415 MB/day, so `maxage=30` never bites. Sizing + the narrower `get`-only variant: `docs/runbooks/apiserver-oidc-agent-identity.md` → "The audit read gap".

- **Cloud's reconciler and Project namespaces (`stacks/cloud`, 2026-11-13)**: Cloud (Forgejo `viktor/cloud`) runs invited Users' code in `p-*` namespaces, so its reconciler is limited by RBAC, admission policies, Pod Security and a Calico floor. The rules follow the M2 contract with the cloud repo, whose rendered names are in its `docs/build/m2-contract-rendered.md`. `tests/cloud-access.test.sh` applies Cloud's real OpenTofu modules (a private App, a public App and a Postgres Service) into kind 1.35 as the reconciler, checks that every object and pod is admitted, then refuses about 130 variants of those objects, one forbidden change each; it also runs a dev Vault. (1) **RBAC split.** ClusterRole `cloud-reconciler` (cluster-wide) holds namespaces, RoleBindings, `bind` on `cloud-reconciler-project` only, read on CRDs (the OpenTofu kubernetes provider looks up every `kubernetes_manifest` type there; the real-apply test found this), `get` on Calico tier `default`, and read on Ingresses and IngressRoutes. Everything a Project contains (Deployments, Kubernetes Services, Ingresses, Secrets, ConfigMaps, ServiceAccounts, quotas, LimitRanges, ExternalSecrets, SecretStores, Calico NetworkPolicies) is in ClusterRole `cloud-reconciler-project`, which the reconciler binds to itself with a RoleBinding in each Project namespace. A single ClusterRoleBinding would have let it read every Secret in the cluster, and admission never sees reads. (2) **ValidatingAdmissionPolicy `cloud-reconciler-scope`** (the first VAP on the cluster): every write by `system:serviceaccount:cloud:cloud-reconciler` must land in a namespace named `p-*` and labelled `cloud.viktorbarzin.me/managed=true`. A namespace it creates or changes must carry that label, `tier=4-aux`, `pod-security.kubernetes.io/enforce=restricted`, `resource-governance/custom-quota=true` and `resource-governance/custom-limitrange=true`, and no label outside the allowlist in `stacks/cloud/access_rules.tf` (keys someone else set may stay unchanged), because labels select NetworkPolicies and Kyverno policies: `chrome-service.viktorbarzin.me/client=true` opens Chrome DevTools on port 9222. It cannot adopt an existing namespace by labelling it. A RoleBinding it writes may bind only `cloud-reconciler-project`, and only to itself. The custom-quota and custom-limitrange labels keep Kyverno from generating `tier-quota` and `tier-defaults`; the reconciler writes the namespace's only ResourceQuota (`cloud-quota`) and LimitRange (`cloud-limits`), each labelled `app.kubernetes.io/managed-by=cloud`. It may write no other quota or limit range, may not change or delete an unlabelled one such as Kyverno's `tier-quota`, and its quota must have no scope, must set requests and limits of CPU and memory and `pods`, and must set PersistentVolumeClaims, LoadBalancers and NodePorts to 0. Between the namespace's creation and the quota's, the namespace has no quota, and Cloud's modules do not order the quota before the Deployments, so a first apply may start pods before the quota exists (each rendered container sets its own limits). (3) **VAP `cloud-externalsecret-store`**: in managed namespaces an ExternalSecret may use only a namespaced SecretStore (`secretStoreRef`, `data[].sourceRef.storeRef`, `dataFrom[].sourceRef`) and no ClusterGenerator, for any user, because the `vault-kv` ClusterSecretStore reads all of `secret/*`. (4) **VAP `cloud-managed-service`**: in managed namespaces a Kubernetes Service is ClusterIP with no `externalIPs`, and a port named `edge` targets the container port named `edge`. Traefik follows ExternalName Services (`allowExternalNameServices` in `stacks/traefik`), so an ExternalName Kubernetes Service plus an Ingress would publish an internal host such as Vault. (5) **VAP `cloud-managed-ingress`**: in managed namespaces an Ingress has class `traefik`, every host is one label under `viktorbarzin.me`, with no wildcard, no host-less rule, no `defaultBackend`, not a reserved App name from the Cloud v1 plan (`auth*`, `login`, `sso`, `account`, `mail`, `vault`, `admin`, `api`, `www`, `status`, `cloud`), and not a host the homelab already routes, and every backend is a Kubernetes Service port named `edge`. Traefik ranks routers by rule length, so without that last check a Project rule such as `Host(nextcloud.viktorbarzin.me) && PathPrefix(/login)` would win over the homelab router on that path. The policy's parameter is ConfigMap `cloud/cloud-taken-hosts`, which `stacks/cloud/taken_hosts.tf` writes at plan time from every Ingress and IngressRoute outside `p-*` namespaces (one key per one-label `viktorbarzin.me` host, the value naming its router); the binding refuses every Project Ingress while the ConfigMap is missing. A host added to the homelab after the last cloud apply is missing until the next apply (the nightly drift plan shows it as a change to that ConfigMap); the reconciler's own taken-host check covers the gap. It refuses `tls.secretName`: Project Ingresses get the wildcard from Traefik's default TLSStore (`traefik/default`), and a Project certificate would join Traefik's global store, where an exact SAN match beats the wildcard for any host. The only annotations allowed are the two Cloud renders: `router.entrypoints` (`websecure`) and `router.middlewares`, which may name only nine shared middlewares in `traefik` (list in `stacks/cloud/access_rules.tf`; Cloud uses `traefik-retry` and `traefik-rate-limit`). Every other key is refused, because cluster-wide controllers act on Ingress annotations: external-dns in `technitium` writes `viktorbarzin.lan` records from `external-dns.alpha.kubernetes.io/*` (a Project could point `wpad.viktorbarzin.lan` anywhere), homepage reads `gethomepage.dev/*`, and external-monitor-sync reads `uptime.viktorbarzin.me/*`. Ingress annotations also reach Middlewares in any namespace, and several (`terminal-tl-proxy-secret`, `ac-gateway-secret`, `agentmd-proxy-secret-wizard`, `browser-bridge-ingress-secret`, `tv-ingress-proof`) add a shared secret header that the Project's own pod would receive. (6) **VAP `cloud-managed-middleware`**: no Traefik Middleware may exist in a managed namespace, for any user. Cloud renders none, and Traefik's CRD provider runs with `allowCrossNamespace = true`, so a Middleware could name a Kubernetes Service in any namespace (errors, forwardAuth), pull in other middlewares (chain, plugin), or hold request bodies in Traefik's memory (buffering). (7) **VAP `cloud-managed-secretstore`**: a SecretStore in a managed namespace must be provider `vault` at `http://vault-active.vault.svc.cluster.local:8200`, path `secret`, version `v2`, Kubernetes auth on mount `kubernetes` with role `cloud-project` as service account `cloud-secrets`, and no other auth method. Otherwise the ESO controller would fetch any URL (webhook provider) or any Vault path of the reconciler's choosing and write the answer into a Project Secret. (8) **VAPs `cloud-managed-pod` and `cloud-managed-deployment`**: the same rules on a pod and on a Deployment's pod template, so a bad Deployment fails at apply time instead of in its ReplicaSet. Volumes are only `emptyDir`, `configMap`, `secret`, `projected` and `downwardAPI`: no PersistentVolumeClaim or `ephemeral` claim on any storage class, and no in-tree `nfs`, `iscsi` or `rbd`, which the kubelet mounts from the node's network past the egress floor (`/srv/nfs` is exported rw with `no_root_squash`). No `runtimeClassName` (the `nvidia` runtime classes reach every GPU without a `nvidia.com/gpu` request), `nodeName`, `nodeSelector`, `affinity` or toleration beyond the API server's default not-ready and unreachable ones (a control-plane toleration would put a pod on `k8s-master`, whose disk etcd shares). No host network, PID or IPC, no init containers, service account `default` only (`cloud-secrets` is the SecretStore's Vault identity), priority class `tier-4-aux` or none (Kyverno's `inject-priority-class-from-tier` fills in a class only when a pod has none, so a pod could otherwise ask for `tier-0-core` or `system-node-critical` and preempt homelab workloads), and resources only `cpu`, `memory` and `ephemeral-storage`, so no GPU. The GPU rule runs before the priority rule: Kyverno's `inject-gpu-workload-priority` gives a GPU pod class `gpu-workload` before admission, and the refusal names the GPU. Every Deployment's pods are labelled `cloud.viktorbarzin.me/component` `app` or `oauth2-proxy`; an App's pod template holds a container named `cookie-strip` running the pinned Caddy image with a port named `edge`, and no other container may declare a port named `edge`. `cookie-strip` runs exactly as Cloud renders it: its fixed `args`, env only `XDG_CONFIG_HOME` and `XDG_DATA_HOME` with their values, no `command`, `envFrom`, lifecycle hook or exec probe (the Caddy image has `/bin/sh`), a `strip-*` ConfigMap mounted whole and read-only at `/etc/caddy`, and an emptyDir at `/run/caddy` that no other container mounts. It sets its own `runAsUser`, and every other container runs as another uid, set on the container or the pod: two sockets share a port with `SO_REUSEPORT` only under the same uid, so App code under cookie-strip's uid could take a share of Traefik's connections unstripped. No pod may share its process namespace. (9) **The cookie boundary.** The homelab's forward-auth cookies (`authentik_proxy_*`, `tsgate`, `anubis`; `cookie_domain = viktorbarzin.me` in `stacks/authentik`) reach every Project host. Cloud's `cookie-strip` container removes them before a request reaches the App, and (4), (5) and (8) make it the only way in: Ingress, then Kubernetes Service port `edge`, then container port `edge`, which only `cookie-strip` may have. VAP `cloud-managed-strip-config` fixes what it strips: a ConfigMap named `strip-*` in a managed namespace holds only the key `Caddyfile`, and that file must match Cloud's `modules/app/Caddyfile.tftpl` line by line (`local.cloud_caddyfile_lines` in `stacks/cloud/access_rules.tf`). Only leading comments, indentation, the App port on 127.0.0.1, the sign-in host, the cookie list and, for a private App, the two blocks that ask `auth-<app>.<namespace>` (this App's own oauth2-proxy, the names filled in by the policy) may vary, and the cookie list must hold `authentik_proxy_*`, `tsgate*` and `anubis*`. Cloud's `cookie-strip.test.ts` runs the file in the pinned image, and M4's live cookie test checks it end to end. **Open, for the contract:** the live Anubis cookie is `techaro.lol-anubis-auth` (`docs/post-mortems/2026-07-14-anubis-x-real-ip-cookie-flap.md`), which `anubis*` does not match, and Cloud's `strip_cookies` validation refuses a dot. The Anubis cookie is a proof-of-work pass, not a session, so a Project App that reads it can skip the Anubis challenge on other hosts; it gets no sign-in. (10) **Pod Security.** The reconciler must label each namespace `enforce=restricted`, so the built-in, fail-closed PSA controller refuses privileged pods, host namespaces and ports, added capabilities, root and hostPath; Kyverno's privileged and host-namespace policies fail open. **What admission cannot see:** Calico NetworkPolicies are served by the aggregated Calico API server, which kube-apiserver admission does not see; for them the per-namespace RoleBinding is the boundary, and the reconciler may write them only in the default tier. (11) **Network floor.** Calico tier `cloud` (order 500, before the admin tiers and `default`) holds GlobalNetworkPolicy `cloud.project-egress-floor`, owned by `stacks/cloud` (M2 contract point 2, Viktor's decision): for every pod in a managed namespace it allows DNS to the kube-dns ClusterIP (which node-local-dns answers) and to the CoreDNS pods (used while node-local-dns restarts), TCP 5432 to the CNPG primary pods in `dbaas`, and TCP 9000 from pods labelled `cloud.viktorbarzin.me/component=oauth2-proxy` to the Authentik server pods; it passes traffic to other managed namespaces (the Project policy keeps only its own) and to the internet minus RFC 1918, CGNAT, link-local, loopback, the home WAN IP `176.12.22.76`, IPv6 unique-local, link-local and loopback and the homelab's Hurricane Electric prefixes, and denies everything else. Cloud's own Project policy excludes the same list, and the test compares the two. Each IP family has its own rule, because Calico refuses a rule that mixes them. The reconciler has no right in that tier, so its Project policies can only narrow access: an Allow-all it writes cannot reach Vault, the LAN or another namespace's Kubernetes Service. Inside the cluster `*.viktorbarzin.me` resolves to Traefik's LoadBalancer address, which stays denied, so Project pods reach no homelab host by its LAN path; opening Traefik would open every LAN-only host as well, because Traefik sees the pod's 10.10.0.0/16 address, which `local-only` and `home-lans-only` admit. **Open risk, for Viktor:** Project pods reach the internet through the home WAN IP, so a request from a Project to a homelab public host through Cloudflare arrives with `Cf-Connecting-Ip` 176.12.22.76, which CrowdSec whitelists (`stacks/crowdsec`, whitelist-trusted-ips), and mx2's node_exporter (9100, OCI security list) admits that /32 too. Abuse sent from a Project also carries the home IP. Denying the WAN IP closes only the direct hairpin; the options are a separate egress path for Projects (`homelab how "VPN egress"`) or scenario-scoped CrowdSec exceptions in place of the blanket whitelist. kind has no Calico, so the test checks the floor as data only; M4's live isolation test covers it. (12) **Kyverno.** `sync-tls-secret` and `sync-registry-credentials` skip namespaces labelled `cloud.viktorbarzin.me/managed=true` (`stacks/kyverno/modules/kyverno/generate-conditions.tf`), so neither the `*.viktorbarzin.me` private key nor the Forgejo cluster-puller token is in a Project namespace, where the reconciler reads Secrets. `strip-cpu-limits` skips them too, because Cloud's quota counts `limits.cpu` and quota admission, which runs after Kyverno, would refuse a pod whose CPU limit was removed. Kyverno's five Deny ValidatingPolicies (deny-host-namespaces, deny-privileged-containers, require-gpumem-declaration, require-trusted-registries, restrict-sys-admin) apply to `p-*` namespaces (none is on the exclude list), and `p-*` is not on the `ghcr-credentials` allowlist, so the admin PAT never reaches a Project. (13) **Authentik** (M2 contract point 1): Authentik RBAC cannot limit group names, policy binding targets or group parents, so the reconciler's role creates no group or binding and reads no user. It may create OAuth2 providers and applications, change and delete only the ones it created (initial permissions), and read flows, certificate key pairs and scope mappings; a plan-time read-back fails the authentik plan if the live role holds anything else. A private App's oauth2-proxy admits only the email allowlist Cloud renders, which trusts the email in Authentik's token; that holds while `default_user_change_email = false` (`stacks/authentik/system-settings.tf`). A stolen token can still create OAuth2 clients with any redirect URI, so a user who follows a crafted authorize link hands that client their profile and email. `app-access-guard.tf` exempts a Cloud application with no binding (slug `cloud-*`, name `Cloud: *`, provider `cloud-*`). **Blocked, for Viktor:** with `core_default_app_access` off, an application with no binding admits nobody, so sign-in to a private App fails at Authentik's authorize step, before oauth2-proxy sees an email. The contract assumed unbound applications admit every Authentik user. It fails closed: no one reaches a private App. The options, in the order the cloud repo's `docs/build/m2-contract-rendered.md` lists them, are one infra-owned OAuth2 provider and application, bound by infra and shared by all private Apps (Cloud then renders no Authentik objects and the reconciler role here drops its grants); a narrowly scoped binding right for the reconciler (Authentik RBAC has none today: `add_policybinding` checks no permission on the target, the grant the contract refused); or `core_default_app_access` back on (every unbound application then admits everyone, and the guard only detects one after the fact). Until Viktor chooses, Cloud's Plan tells the User on every private App that no one can open it (`PRIVATE_SIGN_IN_BLOCKED` in Cloud's `src/lib/plan.ts`), and the M2 sign-off states that private Apps are unreachable. The choice goes into contract point 1, `stacks/authentik/cloud-reconciler.tf` and this paragraph together.

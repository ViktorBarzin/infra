- **NetworkPolicy default-deny egress (wave 1)**: observe-then-enforce (γ approach) — Calico flow logs cluster-wide + GlobalNetworkPolicy log-only on tier 3+4, build empirical allowlist after 1 week, phased per-namespace enforce starting `recruiter-responder`. Tier 0/1/2 deferred. **The internal (ns-to-ns) half of each allowlist now derives faster from the east-west flow trail** (below): `SELECT DISTINCT dst_ns FROM edge WHERE src_ns='<ns>' AND action='allow'`. **External egress IS in that table since 2026-09-01** (`WHERE dst_type='network'` gives the internet destinations with their ports) — it used to be deleted, not merely absent, so the Calico flow-log W1.6 snapshot is no longer the only source. What the table still cannot give is the peer ADDRESS: Goldmane's proto carries no IP field at all, so a CIDR-scoped egress rule still needs the flow-log snapshot or netflow. Enforce-flips remain out of scope of the trail (observe-and-derive only; beads `code-8ywc`).
- **East-west flow trail (who-talks-to-whom, ADR-0014)**: Calico **Goldmane** (`goldmane.calico-system:7443`, gRPC/mTLS, ~60-min in-memory ring buffer — no etcd writes) + **Whisker** live UI (`whisker.viktorbarzin.me`, Authentik-gated) → **`goldmane-edge-aggregator`** streams Goldmane's `Flows.Stream` over mTLS and upserts the per-workload **edge set** into **CNPG DB `goldmane_edges`** (`edge`: src/dst namespace + workload + endpoint type, dst service + namespace, dst port, action, first/last seen, flow count — **widened 2026-09-01**, design `docs/plans/2026-09-01-service-identity-and-request-attribution-design.md` step 2; before that it was `(src_ns,dst_ns,action)` alone). **Aggregation is per WORKLOAD, not per pod** — Goldmane's endpoint name is the generated pod-set name (`traefik-7cbc567497-*`), so it is reduced to the stable workload (`traefik`) or a redeploy would add a row per rollout and a CronJob a row per tick; Whisker serves live per-pod detail. **The old `src_ns == dst_ns` drop rule also DELETED any flow with a non-workload end at BOTH ends** — Goldmane writes the literal `-` for such an end, so `('-','-')` matched the self-edge test. The test is now on endpoint TYPE (`workload`/`host`/`networkset`/`network`/`unknown`), so a genuine self-edge is still dropped while node and internet flows are kept and labelled. **But measure before repeating the design's framing: that deleted class is EMPTY today** — 0 of 2,168 live flows had `-` at both ends (2026-09-01), because **no Calico HostEndpoints are defined** (`kubectl get hostendpoints` → none) so Goldmane never types an end as `host`. The type test guards a class that appears the moment HostEndpoints exist; the immediate gain is the one-dash class, **1,116 of 2,168 flows (51%)**, which was kept all along but recorded as a bare namespace pair (`keel → -`) with no port, workload or type. Still dropped, now counted by reason in the aggregate log line: `intra-namespace` (both ends workloads in one namespace, the class awaiting a keep/drop decision) and `non-workload` (an end with no identity at all). **`homelab edges` output is unchanged** — it groups back up to `(src_ns,dst_ns,action)`; per-workload/port detail needs SQL or the coming Grafana dashboard. **Rows written before the widening are kept** with `-`/`unknown`/`0` sentinels, so a query on the new columns should add `src_type <> 'unknown'`; and because the identity tuple is wider, the FIRST digest after the deploy reports the whole re-observed graph once → daily **`goldmane-edges-digest`** CronJob posts first-seen edges to `#alerts` (consolidated to `#alerts`; the `#security` channel was abandoned 2026-06-25 — the shared webhook's Slack app isn't a member of it, so a `#security` override 404s; see runbook). **CERT-REUSE GOTCHA**: the aggregator's mTLS client cert reuses the operator's Tigera-CA-signed `whisker-backend-key-pair` Secret (Goldmane verifies CA-chain only) — **re-apply `stacks/goldmane-edge-aggregator` if the operator rotates it** (symptom: no `last_seen` updates, `AggregatorDown`). Service identity = namespace, + `service-identity` label only in `monitoring`/`kube-system`/`dbaas`. Health: `AggregatorDown` + `DigestFailing` alerts + cluster-health #48. **WHISKER-WEDGE GOTCHA** (2026-06-28): the operator's `whisker` NetworkPolicy allows DNS egress only to kube-dns *pods*, but whisker-backend resolves goldmane via the kube-dns *ClusterIP* — Calico drops UDP DNS to a ClusterIP under a podSelector-only egress rule, so when whisker-backend's gRPC stream breaks and it re-resolves, it wedges and the UI goes **empty** (the aggregator, a separate pod, is unaffected). FIX = additive egress NP `whisker-allow-dns-clusterip` (`stacks/calico`, allows whisker→10.96.0.10/32:53); the `whisker-watchdog` CronJob is a backstop. Manual heal `kubectl -n calico-system delete pod -l k8s-app=whisker`. Runbook: `docs/runbooks/goldmane-flow-trail.md`. (Goldmane is OSS tech-preview — reversible operator-CR toggle in `stacks/calico/main.tf`.)
- **Who reached the kube-apiserver (design step 4, 2026-09-01)**: the apiserver already carries `--authentication-config=/etc/kubernetes/pki/auth-config.yaml` with the `kubernetes` + `k8s-dashboard` OIDC issuers, Terraform-owned in `stacks/rbac/modules/rbac/apiserver-oidc.tf` over SSH and **byte-identical to the node** (sha256 `bdefc260…97e16`, cross-checked against the apiserver's own `apiserver_authentication_config_controller_last_config_info{hash}` metric — that metric is the fastest way to confirm which config is live, and the file is hot-reloaded, so an issuer change needs NO restart and NO manifest edit). There are **no `--oidc-*` flags and none wanted** (legacy flags allow one issuer). Measured: **zero** OIDC-authenticated audit events in 24h, while the shared kubeadm admin cert (`kubernetes-admin`, `credential-id X509SHA256=7a03b1f4…0616`, expires 2027-04-17) produced 116 mutating events in 1h — every human, agent and cron job on the devvm shares it, so the audit log cannot tell them apart. Landed inert: a `kubernetes-agent` Authentik app (`stacks/rbac/authentik-kubernetes.tf`), a **third issuer prefixing username AND groups with `agent:`** behind `var.agent_oidc_enabled` (**default false — with it off the rendered config is byte-identical, so the null_resource trigger does not move and an apply cannot touch the control plane**; flipping it needs a LOCAL apply with `TF_VAR_ssh_private_key` + `-replace`, because CI has no SSH key), and group-keyed ClusterRoleBindings (`oidc-group-bindings.tf`) for `kubernetes-*` and `agent:kubernetes-*`. The prefix is load-bearing: the audit event records `user.username`/`user.groups` and NOT the issuer, so a second client on one issuer would stay indistinguishable, and the prefix also means an agent inherits no human binding (agents are bound read-only). Verify with `kubectl --context agent@homelab auth whoami`. Break-glass stays the shared cert (authenticates via `--client-ca-file`, so an Authentik outage cannot block it) — note `scripts/t3-provision-users.sh` reads that same kubeconfig as `ADMIN_KUBECONFIG`, so retiring it is a provisioning change too. Runbook `docs/runbooks/apiserver-oidc-agent-identity.md`.
- **NO Kubernetes read is audited anywhere, and TWO audit policies exist with only one live (2026-09-01)**: the apiserver reads `/etc/kubernetes/audit-policy.yaml` (hand-deployed from `scripts/k8s-apiserver-audit-policy.yaml`, whose rule 1 is `level: None` on `get,list,watch`), while `stacks/rbac/modules/rbac/audit-policy.tf` writes a DIFFERENT policy to `/etc/kubernetes/policies/audit-policy.yaml` that nothing reads — its rules WOULD have logged reads. The log path and rotation flags disagree too. **Left inert on purpose**: its `triggers` are content hashes, so changing them re-runs an SSH provisioner that rewrites the apiserver manifest and restarts the API on the single control-plane node, and CI applies that stack with no SSH key. Measured 6h: 74,060 audit events (update 40,353 / create 21,368 / delete 10,082 / patch 2,257), **zero reads**, against 366,219 read requests served. Auditing Secret reads would cost ~+147 MB/day (+36% audit volume, **+4.2%** of Loki's 3.54 GB/day) and lands on apiserver disk + Loki, **never etcd** (etcd is not even scraped). Also corrected: on-node audit history is **~2.8 days, not 30** — `maxsize=100`/`maxbackup=10` rotates every 6-7h at ~415 MB/day, so `maxage=30` never bites. Sizing + the narrower `get`-only variant: `docs/runbooks/apiserver-oidc-agent-identity.md` → "The audit read gap".

- **Cloud's reconciler and Project namespaces (`stacks/cloud`, 2026-11-13)**: Cloud (Forgejo `viktor/cloud`) runs invited Users' code in `p-*` namespaces, so its reconciler is limited by RBAC, admission policies, Pod Security and a Calico floor. The rules follow the M2 contract with the cloud repo, whose rendered names are in its `docs/build/m2-contract-rendered.md`. `tests/cloud-access.test.sh` applies Cloud's real OpenTofu modules (a private App, a public App and a Postgres Service) into kind 1.35 as the reconciler, checks that every object and pod is admitted, then refuses about 190 variants of those objects, one forbidden change each. It then applies each of Cloud's snapshot fixtures (`render.fixtures.ts`: one App, one Postgres with quota pods 0, a private App with an allow list, a Service removed, hostile env values and the rest) the same way and admits each object and a pod from each template again. It also runs a dev Vault. (1) **RBAC split.** ClusterRole `cloud-reconciler` (cluster-wide) holds namespaces, RoleBindings, `bind` on `cloud-reconciler-project` only, read on CRDs (the OpenTofu kubernetes provider looks up every `kubernetes_manifest` type there; the real-apply test found this), `get` on Calico tier `default`, and read on Ingresses and IngressRoutes. Everything a Project contains (Deployments, Kubernetes Services, Ingresses, Secrets, ConfigMaps, ServiceAccounts, quotas, LimitRanges, ExternalSecrets, SecretStores, Calico NetworkPolicies) is in ClusterRole `cloud-reconciler-project`, which the reconciler binds to itself with a RoleBinding in each Project namespace. A single ClusterRoleBinding would have let it read every Secret in the cluster, and admission never sees reads. (2) **ValidatingAdmissionPolicy `cloud-reconciler-scope`** (the first VAP on the cluster): every write by `system:serviceaccount:cloud:cloud-reconciler` must land in a namespace named `p-*` and labelled `cloud.viktorbarzin.me/managed=true`. A namespace it creates or changes must carry that label, `tier=4-aux`, `pod-security.kubernetes.io/enforce=restricted`, `resource-governance/custom-quota=true` and `resource-governance/custom-limitrange=true`, and no label outside the allowlist in `stacks/cloud/access_rules.tf` (keys someone else set may stay unchanged), because labels select NetworkPolicies and Kyverno policies: `chrome-service.viktorbarzin.me/client=true` opens Chrome DevTools on port 9222. It cannot adopt an existing namespace by labelling it. A RoleBinding it writes may bind only `cloud-reconciler-project`, and only to itself. The custom-quota and custom-limitrange labels keep Kyverno from generating `tier-quota` and `tier-defaults`; the reconciler writes the namespace's only ResourceQuota (`cloud-quota`) and LimitRange (`cloud-limits`), each labelled `app.kubernetes.io/managed-by=cloud`. It may write no other quota or limit range, may not change or delete an unlabelled one such as Kyverno's `tier-quota`, and its quota must have no scope, must set requests and limits of CPU, memory and ephemeral storage and `pods` (so quota admission refuses a pod without those limits), and must set PersistentVolumeClaims, LoadBalancers and NodePorts to 0. Between the namespace's creation and the quota's, the namespace has no quota, and Cloud's modules do not order the quota before the Deployments, so a first apply may start pods before the quota exists (each rendered container sets its own limits). (3) **VAP `cloud-externalsecret-store`**: in managed namespaces an ExternalSecret may use only a namespaced SecretStore (`secretStoreRef`, `data[].sourceRef.storeRef`, `dataFrom[].sourceRef`) and no ClusterGenerator, for any user, because the `vault-kv` ClusterSecretStore reads all of `secret/*`. (4) **VAP `cloud-managed-service`**: in managed namespaces a Kubernetes Service is ClusterIP with no `externalIPs` and no `prometheus.io/*` annotation. A Service named `edge-<app>` must select `cloud.viktorbarzin.me/component=edge` and `cloud.viktorbarzin.me/service=<app>` and have one port, `edge`, targeting the container port `edge`; a Service named `auth-<app>` must select that App's `oauth2-proxy` pods on one port `http`. Traefik follows ExternalName Services (`allowExternalNameServices` in `stacks/traefik`), so an ExternalName Kubernetes Service plus an Ingress would publish an internal host such as Vault. (5) **VAP `cloud-managed-ingress`**: in managed namespaces an Ingress has class `traefik`, every host is one label under `viktorbarzin.me`, with no wildcard, no host-less rule, no `defaultBackend`, not a reserved App name from the Cloud v1 plan (`auth*`, `login`, `sso`, `account`, `mail`, `vault`, `admin`, `api`, `www`, `status`, `cloud`), and not a host the homelab already routes, and every backend is an `edge-*` Service on port `edge` or an `auth-*` Service on port `http`, by port name, never App pods' own Service. Traefik ranks routers by rule length, so without that last check a Project rule such as `Host(nextcloud.viktorbarzin.me) && PathPrefix(/login)` would win over the homelab router on that path. `stacks/cloud/taken_hosts.tf` collects those hosts at plan time from every Ingress and IngressRoute outside `p-*` namespaces (each one-label `viktorbarzin.me` host and the router that serves it) and writes them into the policy itself as a CEL map literal, in place of the marker `@TAKEN_HOSTS@`. The marker alone is not valid CEL, so the API server refuses a policy applied without the hosts, and the apply fails. The hosts are not a ConfigMap parameter, because calico-apiserver runs the cluster's admission policies too, see (10). A host added to the homelab after the last cloud apply is missing until the next apply (the nightly drift plan shows it as a change to `cloud-managed-ingress`); the reconciler's own taken-host check covers the gap. It refuses `tls.secretName`: Project Ingresses get the wildcard from Traefik's default TLSStore (`traefik/default`), and a Project certificate would join Traefik's global store, where an exact SAN match beats the wildcard for any host. The only annotations allowed are the two Cloud renders: `router.entrypoints` (`websecure`) and `router.middlewares`, which may name only nine shared middlewares in `traefik` (list in `stacks/cloud/access_rules.tf`; Cloud uses `traefik-retry` and `traefik-rate-limit`). Every other key is refused, because cluster-wide controllers act on Ingress annotations: external-dns in `technitium` writes `viktorbarzin.lan` records from `external-dns.alpha.kubernetes.io/*` (a Project could point `wpad.viktorbarzin.lan` anywhere), homepage reads `gethomepage.dev/*`, and external-monitor-sync reads `uptime.viktorbarzin.me/*`. Ingress annotations also reach Middlewares in any namespace, and several (`terminal-tl-proxy-secret`, `ac-gateway-secret`, `agentmd-proxy-secret-wizard`, `browser-bridge-ingress-secret`, `tv-ingress-proof`) add a shared secret header that the Project's own pod would receive. (6) **VAP `cloud-managed-middleware`**: no Traefik Middleware may exist in a managed namespace, for any user. Cloud renders none, and Traefik's CRD provider runs with `allowCrossNamespace = true`, so a Middleware could name a Kubernetes Service in any namespace (errors, forwardAuth), pull in other middlewares (chain, plugin), or hold request bodies in Traefik's memory (buffering). (7) **VAP `cloud-managed-secretstore`**: a SecretStore in a managed namespace must be provider `vault` at `http://vault-active.vault.svc.cluster.local:8200`, path `secret`, version `v2`, Kubernetes auth on mount `kubernetes` with role `cloud-project` as service account `cloud-secrets`, and no other auth method. Otherwise the ESO controller would fetch any URL (webhook provider) or any Vault path of the reconciler's choosing and write the answer into a Project Secret. (8) **VAPs `cloud-managed-pod` and `cloud-managed-deployment`**: the same rules on a pod and on a Deployment's pod template, so a bad Deployment fails at apply time instead of in its ReplicaSet. Every pod is labelled `cloud.viktorbarzin.me/component` `app`, `edge` or `oauth2-proxy`. Volumes are only `emptyDir` (each with a `sizeLimit`), `configMap`, `secret`, `projected` and `downwardAPI`: no PersistentVolumeClaim or `ephemeral` claim on any storage class, and no in-tree `nfs`, `iscsi` or `rbd`, which the kubelet mounts from the node's network past the egress floor (`/srv/nfs` is exported rw with `no_root_squash`). Every container limits its ephemeral storage, so a Project cannot fill a worker's disk into DiskPressure. No `runtimeClassName` (the `nvidia` runtime classes reach every GPU without a `nvidia.com/gpu` request), `nodeName`, `nodeSelector`, `affinity` or toleration beyond the API server's default not-ready and unreachable ones (a control-plane toleration would put a pod on `k8s-master`, whose disk etcd shares). No host network, PID or IPC, no init containers, no shared process namespace, no `host` in a probe or lifecycle hook (the kubelet would connect from the node's network), service account `default` only (`cloud-secrets` is the SecretStore's Vault identity), priority class `tier-4-aux` or none (Kyverno's `inject-priority-class-from-tier` fills in a class only when a pod has none, so a pod could otherwise ask for `tier-0-core` or `system-node-critical` and preempt homelab workloads), and resources only `cpu`, `memory` and `ephemeral-storage`, so no GPU. The GPU rule runs before the priority rule: Kyverno's `inject-gpu-workload-priority` gives a GPU pod class `gpu-workload` before admission, and the refusal names the GPU. No pod carries a `prometheus.io/*` annotation: the `kubernetes-pods` and `kubernetes-service-endpoints` scrape jobs keep the target's labels (`honor_labels: true`), so a Project endpoint could otherwise write series under homelab labels and mask or fake homelab alerts. An **edge pod** runs exactly Cloud's edge: one container `edge`, the pinned Caddy image (digest), its fixed `args`, env only `XDG_CONFIG_HOME` and `XDG_DATA_HOME` with their values, no `command`, `envFrom`, lifecycle hook, liveness or startup probe, one port `edge` = 8080/TCP with no host port, a `tcpSocket` readiness probe on `edge`, ConfigMap `edge-<its App>` mounted whole and read-only at `/etc/caddy`, and an emptyDir at `/run/caddy`. An **oauth2-proxy pod** runs exactly Cloud's oauth2-proxy: one container, the pinned image (digest), the fixed `args` with only its App's host and `--upstream=http://edge-<app>.<namespace>.svc.cluster.local:80/` filled in (client id `cloud-apps`, the in-cluster issuer, the allowlist file as the only gate, no `--skip-jwt-bearer-tokens`, no `--email-domain`, a host-bound cookie), Secret `auth-<its App>` as its only env, one port `http` = 4180, and ConfigMap `auth-<its App>` read-only at `/etc/oauth2-proxy`. Its component label is also the Calico source that reaches the Authentik server pods, so no other program can carry it and talk to Authentik past Traefik's CrowdSec and rate limits. App pods run any image within the general rules. (9) **The cookie boundary** (M2 contract, Addendum v2 point 8). The homelab's forward-auth cookies (`authentik_proxy_*`, `tsgate`, Anubis's `techaro.lol-anubis-auth`; `cookie_domain = viktorbarzin.me` in `stacks/authentik` and `modules/kubernetes/anubis_instance`) reach every Project host. Cloud's edge, a pinned Caddy in its own Deployment `edge-<app>`, removes them and every `X-Authentik-*` header before a request reaches the App, removes every `Set-Cookie` with a `Domain` attribute on the way back, and caps request and response headers at 64 KB. (4), (5) and (8) make it the only way in: Traefik reaches a Project only through an Ingress, which names only an `edge-*` or `auth-*` Service, which selects only edge or oauth2-proxy pods, which run only Cloud's pinned images and config; the oauth2-proxy's only upstream is the edge. No App code runs in an edge pod, so App code cannot take the edge's port, which it could when the edge was a container in the App pod (an OOM-killed Caddy freed :8080 to App code at once). The ingress floor in (11) lets App pods accept connections only from edge pods. VAP `cloud-managed-edge-config` fixes what the edge does: a ConfigMap named `edge-*` in a managed namespace holds only the key `Caddyfile`, and that file must match Cloud's `modules/app/Caddyfile.tftpl` line by line (`local.cloud_caddyfile_lines` in `stacks/cloud/access_rules.tf`). Only leading comments, indentation and the cookie list may vary, the upstream must be `app-<app>` in the same namespace (filled in by the policy), and the cookie list must hold `authentik_proxy_*`, `tsgate*`, `anubis*` and `techaro.lol-anubis-*`. Cloud's `edge.test.ts` runs the file in the pinned image, and M4's live cookie test checks it end to end. **Residual risk:** App page JavaScript can still set a `Domain=viktorbarzin.me` cookie through `document.cookie`, which the edge never sees. That allows a cookie bomb (about 30 cookies of 4 KB lock a browser out of every homelab host until the user clears cookies), tossing a homelab session cookie (login fixation on forward-auth apps), and it voids `SameSite=Lax` between Apps and homelab apps. The full fix is a separate registrable domain for Apps, about $10 a year, which Viktor declined (Cloud's ADR-0004 and its amendments). (10) **Pod Security.** The reconciler must label each namespace `enforce=restricted`, so the built-in, fail-closed PSA controller refuses privileged pods, host namespaces and ports, added capabilities, root and hostPath; Kyverno's privileged and host-namespace policies fail open. **Calico writes and admission:** Calico NetworkPolicies are served by calico-apiserver, the aggregated API server for `projectcalico.org`. It is built on `k8s.io/apiserver` and runs the ValidatingAdmissionPolicy plugin itself, over every policy in the cluster, so `cloud-reconciler-scope` also keeps the reconciler's Calico writes in managed `p-*` namespaces; the per-namespace RoleBinding and the default-tier rule below are the other two limits. The same plugin makes calico-apiserver fragile: a policy with a `paramKind` starts a cluster-wide informer for that kind in calico-apiserver, and its service account may not list ConfigMaps. When `cloud-managed-ingress` took ConfigMap `cloud-taken-hosts` as its parameter, that informer never synced, calico-apiserver failed readyz, `v3.projectcalico.org` went `Available=False`, every Calico write failed with "the server is currently unable to handle the request", and a deleted namespace stayed Terminating (found 2026-11-13 in kind, before any apply). On the cluster that would stop every `projectcalico.org` read and write and stall namespace deletion everywhere. Deleting the policy does not heal it: calico-apiserver keeps the informer and stayed unready 5 minutes after the policy was gone, until its pods were restarted. So no policy in `stacks/cloud` takes a parameter, and any new ValidatingAdmissionPolicy with a `paramKind`, from any stack, needs read on that kind for `calico-system:calico-apiserver` first. (13) **Authentik** (M2 contract, Addendum v2 point 7, which replaced point 1): Cloud's reconciler creates no Authentik object and holds no Authentik credential. Authentik RBAC cannot limit group names, policy binding targets or group parents, and with `core_default_app_access` off an unbound application admits nobody, so this repo owns one OAuth2 provider and application, `cloud-apps` (`stacks/authentik/cloud-apps.tf`), shared by every private App: a confidential client `cloud-apps`, redirect URIs in regex mode matching only `^https://[a-z][a-z0-9-]{0,29}[a-z0-9]\.viktorbarzin\.me/oauth2/callback$`, RS256, scopes openid, profile and email, bound to policy `cloud-apps-active-users` and listed in `app_access_exempt`. Its client id and secret are in `secret/cloud/system`, which only the reconciler reads. Each private App's oauth2-proxy admits only the App's email allowlist (ConfigMap `auth-<app>`), with its own cookie secret and a cookie bound to the App's host, so one App's session does not open another. The allowlist trusts the email in Authentik's token. Users cannot change their email (`default_user_change_email = false`, `stacks/authentik/system-settings.tf`), but the `invitation-enrollment` flow asks for an email and never checks it, and Authentik does not require emails to be unique, so an invitee could enroll as someone else's address. `cloud-apps-active-users` therefore admits an active, signed-in account only when its email is vouched for: Authentik recorded a social source enrolling it (`goauthentik.io/user/sources`, written only by the enrolling write stage, never by linking a source later), or it is on path `users/email-verified` (passkey signup, inactive until the emailed link is followed), or an admin set `attributes.cloud_apps_email_vouched: true`. It refuses `guest`, service accounts and every account with `attributes.proxy_only`, which the proxy invitation stamps, also onto a signed-in account that reruns `invitation-enrollment` and rewrites its email there. Any other invitation on `invitation-enrollment` must carry `attributes.proxy_only` as well (`stacks/authentik/proxy-enrollment.tf`). An account made before Authentik recorded sources needs the admin attribute before it can open a private App. The reconciler copies the client secret into each namespace with a private App (`_cloud/<app>-oauth2-proxy`, read only by External Secrets and the reconciler; App pods have no API token). With it and a host that matches the redirect pattern, someone can redeem codes for that host and read the signed-in user's profile and email; Cloud's Ingress rules keep Project hosts off homelab hosts. Not done: narrowing Authentik's trusted proxy CIDRs to Traefik's addresses; with the oauth2-proxy pinned in (8), no Project code reaches Authentik directly.

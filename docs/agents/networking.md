# Networking and resilience

Moved verbatim from the repo's agent instruction files (`AGENTS.md`, `.claude/CLAUDE.md`) on 2026-09-22, when the two merged into one root `AGENTS.md`. Related as-built docs: `docs/architecture/networking.md`, `docs/architecture/security.md`.

## Networking & Resilience
- **Critical path services scaled to 3**: Traefik, Authentik, CrowdSec LAPI, PgBouncer, Cloudflared.
- **PDBs**: minAvailable=2 on Traefik and Authentik.
- **Fallback proxies**: basicAuth when Authentik is down, fail-open when poison-fountain is down.
- **CrowdSec enforcement has TWO surfaces, split by what can identify the client** (pivoted 2026-08-18 off the Cloudflare edge): (1) **all HTTP, proxied included** → the in-process **`crowdsec` Traefik plugin** on the **`websecure` ENTRYPOINT** (`stacks/traefik/modules/traefik/crowdsec-bouncer-plugin/` + the Middleware in that module's `middleware.tf`). Entrypoint, not per-ingress, so it is prepended to every router on it — all ~195 Ingresses, the 10 IngressRoutes and the catchall, including the hand-rolled ones that bypass `ingress_factory`; a `modules/` change would otherwise fan across 33 platform + ~95 app stacks applied serially, where lock-contended stacks are SKIPPED not failed. Polls LAPI `/v1/decisions` every 30s into an in-memory set, one map lookup per request, 403 on a hit. **Client IP comes from the unspoofable TCP peer** — `Cf-Connecting-Ip`/`X-Forwarded-For` honoured ONLY from `trustedProxyCIDRs` (`10.10.0.0/16`, cloudflared); any other peer is judged on itself, because pfSense NATs WAN :443 straight to Traefik so a banned client can connect directly and claim to be anyone. **Ban-only** (the plugin honours `ban` and ignores `captcha`). **The `captcha_remediation` profile was REMOVED on 2026-09-02** — it diverted `http-429-abuse`, `http-403-abuse`, `http-crawl-non_statics` and `http-sensitive-files` to a captcha decision that nothing enforces, so those four detected and did nothing. It cost us: a Meta crawler swarm walked forgejo's git history that day and OOMKilled all three traefik pods plus forgejo, while `http-crawl-non_statics` fired **60 times** and every decision was discarded. All four now fall through to `default_ip_remediation` and ban for 4h. They are genuinely FP-prone, which is why the divert existed — the mitigation is the trusted-ips whitelist, which now pins the **London egress (137.220.71.46)** as well as the origin; that address was self-banned for 363 days once already. **If a legitimate source starts getting banned, whitelist it — do not reintroduce a remediation that goes nowhere, because the metrics then look like coverage.** Meta's announced space (117 collapsed ranges from AS32934/63293/54115) is a Terraform-managed static blocklist, re-imported daily at 04:00 by `crowdsec-blocklist-import` so its 168h decisions never lapse; the accepted cost is no FB/Instagram/WhatsApp/Messenger link previews for our URLs), handles `scope=Range`, **CAPI EXCLUDED** via the `origins` config, auth hosts (`authentik`, `public-auth`) never gated, `dryRun` flag. **Consequence: the enforced set is currently 4 decisions** — this is new coverage for web traffic, not a like-for-like replacement of a 22.7k blocklist. **Fail-open is structural** (no backend to be unreachable; LAPI down → last known set, never loaded → allow) — which is WHY it is in-process and not a ForwardAuth: `forward.go` answers 500/502 on an unreachable auth backend with no allow option (the reason `auth-proxy`/`bot-block-proxy` exist as shims), and a ForwardAuth peer is always a Traefik pod so peer-trust is unimplementable there. Bouncer key `traefik`. (2) **direct hosts + non-HTTP ports** → `cs-firewall-bouncer` DaemonSet drops **in-kernel via nftables** in BOTH the `input` and `forward` hooks (Traefik is ETP=Local so client traffic is DNAT'd to the pod via `forward`); pulls ALL decisions incl. the CAPI blocklist (22,715 of 22,719 live on 2026-08-18). **This covers almost no public web traffic** — `cloudflare_proxied_names = []` so every HTTP host is proxied and the node only sees 10.10.x.x. **The whitelist is PARSER-stage: a manual `cscli decisions add` on an internal IP IS enforced in-kernel on every node** — banning 10.0.10.10 blackholed the devvm incl. its DNS (2026-08-18; `decisions delete` recovered in ~3s). Test with `192.0.2.1`, not your own address. **Unban now takes ~33s** (one poll) vs a ~72h floor at the edge. **Cloudflare edge channel RETIRED 2026-08-18**: the Lists API holds a hard ~72h floor between successful item writes (audit log, full list history: 8 of 16 intervals in [72h, 72h+120s), three at exactly 259,200s, nothing between 4.5h and 72h; rejected attempts do NOT consume it), which left the edge list disagreeing with LAPI for **107 of 216 observed hours**; a hand-ban on our own WAN egress reached the edge 2 days later and blocked every proxied host. List + token + `crowdsec-cf-sync` CronJob + `lapi_kv_sync.py` + the `kvsync` key (and its 442 leaked LAPI rows) all deleted. **`cloudflare_ruleset.crowdsec` was deliberately NOT destroyed** — it is the zone's `default` `http_request_firewall_custom` PHASE ENTRYPOINT, so a DELETE would wipe the zone's whole custom-rules phase; it was reduced to its pre-existing disabled `skip` rule and detached with `removed { lifecycle { destroy = false } }` (the repo's first `removed` block). CF managed DDoS L7 + Bot Fight Mode are independent and untouched. Alerts followed the enforcement: the 3 `CrowdSecEdge*` rules are gone, replaced by `CrowdSecL7BouncerNotPolling` (Prometheus, off `cs_lapi_bouncer_requests_total{bouncer="traefik"}`, guarded on LAPI being up since the series goes ABSENT not flat), plus Loki `CrowdSecL7BouncerRefreshFailing` and `CrowdSecL7BlockBurst` (the latter guards the new feedback loop: blocked requests now reach Traefik and are access-logged, so mass 403s can trip `http-403-abuse`). The plugin runs under Yaegi where Prometheus counters are not cheap, so decisions are log lines `[crowdsec-bouncer] action=...` on traefik stdout. **BEFORE APPLYING ANY vendored-plugin change run `scripts/yaegi-plugin-gate`** — one broken plugin disables ALL Traefik plugins incl. `api-token-middleware` (paperless-mcp, repowise), and `go build`/`go test` do NOT catch it: this plugin passed 26 tests while panicking Yaegi at import because it held a **variadic func in a STRUCT FIELD** (fine as a parameter or package-level func, fatal in a field). **THE AGENTS MUST POLL THE TRAEFIK LOG (2026-09-03).** The chart renders every `agent.acquisition` entry with `poll_without_inotify: false`, and with inotify alone an agent keeps reading a file rotated or replaced by a container restart — measured with the live container on `traefik/3.log` while the agent held an fd on `traefik/2.log` from the previous evening, lines-read frozen at 54,238 across 80 fresh requests. Traefik restarted 5x during the incident and kubelet rotates its log every 1.5-3h (JSON access log since 2026-09-01), so **CrowdSec saw traefik for ~2h after each agent restart and was then blind**, starving every `http_*` scenario. The traefik entry now lives in `kubernetes_config_map.crowdsec_traefik_acquisition` with polling on; the chart's mailserver entries still have the fault. **PER-IP DETECTION CANNOT CATCH A DISTRIBUTED CRAWL** — Meta used 61-63 addresses, each its own `/64`, at 0.059-0.121 req/s, and with buckets being per-agent across 3 traefik replicas, capacity 10/6/4 each catch 0 of 63 (capacity 2 catches 19 while banning any human viewing 3 pages). `viktor/forgejo-crawl-slow` catches faster crawlers, not this one. What stops Meta is the Terraform-managed static blocklist (117 collapsed ranges from AS32934/63293/54115, re-imported daily at 04:00 so the 168h decisions never lapse). **Cloudflare's `ai_bots_protection` does NOT catch it either** (enabled 2026-09-03, kept on for declared crawlers): of 73 residual Meta requests, 66 arrived THROUGH the cloudflared tunnel, because Cloudflare verifies bots by ASN and reverse DNS and Meta sent spoofed Chrome user-agents. Sending `meta-externalagent`/`GPTBot`/`ClaudeBot` UAs from our own address returns 200 and is not a valid test. Full as-built: `docs/architecture/security.md`; manual bans: `docs/runbooks/crowdsec-manual-bans.md`.
- **Rate limiting**: Return 429 (not 503). Per-service tuning via dedicated middleware + `skip_default_rate_limit` (default 10/s burst 50): Immich 1000/20000, ActualBudget 50/300 (app boot = ~70 parallel revalidations), authentik 100/1000 on `/`+`/static` (login SPA cold-loads ~70 flow chunks from `/static`; default burst 429'd them → blank login screen).
- **Retry middleware**: 2 attempts, 100ms — in default ingress chain.
- **Entrypoint transport timeouts** (`websecure` `respondingTimeouts`): `writeTimeout=0` (unlimited download duration), `readTimeout=3600s` (uploads ≤1h), `idleTimeout=600s`. These are **HARD total-duration caps**, not nginx-style per-read idle timeouts — a finite `writeTimeout` truncates *any* large download at that wall-clock mark (a prior `writeTimeout=60s` silently cut Immich videos at 60s). **Do NOT re-tighten `writeTimeout`**; keep `readTimeout` finite (slow-loris backstop) but ≥ longest expected upload. Full rationale: `docs/architecture/networking.md` → "Entrypoint Transport Timeouts".
- **HTTP/3 (QUIC)**: Enabled on Traefik. Works for **direct (non-proxied) apps** via the dedicated LB IP below (ETP=Local). Proxied apps get QUIC at the Cloudflare edge. **It depends on a NODE sysctl and breaks silently without it (2026-08-29):** Traefik terminates h3 on ONE shared UDP socket per pod, and quic-go's buffer request is capped by `net.core.rmem_max`. A node at the Ubuntu default (`212992`) gives a `425984`-byte socket that overflows on ACK bursts — quic-go loses ACKs, the transfer stalls ~30s and dies, and because Traefik already wrote its `200` + `Content-Length` the access log shows an ordinary success with a short body while the client saves a **truncated file** (a cut JPEG renders correct on top and flat grey below). Measured over 7 days: h3 truncated **54 of 69** large Immich downloads, h2 truncated **0**; after the fix h3 truncations went to zero. `playbooks/k8s-node-tuning.yml` sets `rmem_max`/`wmem_max` = `7500000` (quic-go's documented value) on all 6 nodes; a sysctl change needs a Traefik roll to take effect (quic-go reads the limit once, at socket creation). **The counter is per-NETNS and the node-exporter DaemonSet cannot see it** — it runs `hostNetwork: true` and read 0 for the whole incident while the pod's own counter was 449. Read it with `PID=$(pgrep -x traefik); sudo nsenter -t $PID -n ss -uanpm | grep -A1 ':8443'` (expect `rb=14680064`, `d0`), or rely on the `quic-socket-metrics` sidecar + `TraefikQUICSocketDropping` alert. Full detail: `docs/architecture/networking.md` → "HTTP/3 depends on a node sysctl".
- **Traefik memory limit is 1536Mi, request 768Mi (raised 2026-09-02).** All three pods were OOMKilled repeatedly (exit 137) at the old 768Mi request=limit and every ingress flapped, under a crawler swarm on forgejo's commit/src/blame pages. Between restarts traefik sat at 681Mi of 768Mi, i.e. permanently at the ceiling. The request deliberately stays 768Mi (so Burstable, not Guaranteed): node2/node3 have only ~2.2-2.7GiB of free memory REQUESTS while running at ~40% actual, so raising the request on three replicas would spend 2.3GiB of reservation and eat the N-1 headroom `ClusterCannotTolerateNonGpuNodeLoss` watches. **Still unexplained:** the pods came back at 193-263Mi having climbed to 681Mi over 35h, so that is growth over time, not the spike alone — the access log went JSON on 2026-09-01 and now retains User-Agent and Referer, which is the first thing to rule out.
- **Traefik LB IP = `10.0.20.203`, `externalTrafficPolicy: Local`** (dedicated, NOT the shared `.200`). Moved off the shared `.200` on 2026-05-30 so direct/non-proxied apps preserve the **real client IP for CrowdSec** (ETP=Cluster SNAT'd them to the node IP) and so QUIC works. **The shared `10.0.20.200` keeps the other 8 LB services** (PG state-backend `postgresql-lb`, headscale, wireguard, xray, etc. — all ETP=Cluster; MetalLB forbids mixed ETP on a shared IP, hence Traefik's own IP). **coturn took its own `10.0.20.205` (ETP=Local) on 2026-08-11** for the same client-IP reason: on the shared IP, kube-proxy's SNAT made coturn report internal addresses to external clients, breaking every WebRTC relay (both neko browsers stalled at ICE `checking`). pfSense alias `coturn_lb`. **cloudflared targets the in-cluster Traefik Service** (`https://traefik.traefik.svc.cluster.local:443`, remote/dashboard tunnel config — edit via CF Global API Key in `secret/platform`), so proxied apps are decoupled from the LB IP. pfSense WAN 443 (tcp+udp) NAT → alias `traefik_lb` (`.203`). Internal split-horizon apex `viktorbarzin.me A` → `.203`. Full runbook + post-mortem: `docs/plans/2026-05-30-traefik-dedicated-ip-etp-local-*`.
- **IPv6 ingress** = HE 6in4 tunnel (`2001:470:6e:43d::2`) → **standalone HAProxy on pfSense** (`/usr/local/etc/ipv6-haproxy.cfg`, NOT the HAProxy package) using `send-proxy-v2` → Traefik `.203` (web 443/80) + mail NodePorts `30125-30128` (25/465/587/993) — so **real IPv6 client IPs reach CrowdSec**. Traefik trusts PROXY-v2 **only from `10.0.20.1`** (`entryPoints.web/websecure.proxyProtocol.trustedIPs`); real IPv4 clients (own source IP) unaffected. **No QUIC over IPv6** (bridge is TCP/h2). Replaced socat 2026-05-30 (socat masked every v6 client as `10.0.20.1`). Boot/persistence: config.xml `<shellcmd>` → `ipv6_proxy.sh` (rebinds every wildcard `listen [::]:<port>` in the nginx config onto the LAN IPv6 to free the tunnel IPv6, then `service ipv6proxy onestart`); `rc.d/ipv6proxy` manages HAProxy. Backends use **no health `check`** (a plain TCP check false-DOWNs the PROXY-expecting listeners). **HAProxy binds all six frontends or none, so one busy port kills web AND mail over IPv6** — the rebind guard used to test for the literal `[::]:443`, which stopped matching when the webConfigurator moved to 8443; nginx kept wildcard `*:80`, HAProxy could not bind `[TUNNEL]:80`, and the bridge stayed down for 29 days after the 2026-07-18 reboot with nothing alerting (IPv4 fine, Cloudflare-proxied hosts reach the origin over IPv4, so only the ~31 `non-proxied` ingresses + IPv6 mail were dark). The guard is port-agnostic since 2026-08-16 and the script logs whether `[TUNNEL]:443` came up. **Signature of a down bridge:** IPv6 443 = `connection refused`, IPv6 80 = pfSense nginx `301` → `https://<host>:8443/` (its login page + self-signed cert, which a browser follows instead of falling back to IPv4), while `ping6` to the tunnel address still answers. As-built: `docs/architecture/networking.md` → "IPv6 Ingress".

The LAN has no IPv6 internet, and A1 offers no native IPv6 on the line. Declared in `scripts/pfsense-sofia-lan-ula-ra.php`: re-run it instead of saving the WAN tab of Services > Router Advertisement, whose router-lifetime input refuses 0. pfSense forces a `route ::/0` option into every RA, set to low preference. - **IPAM & DNS auto-registration**: pfSense Kea DHCP serves all 3 subnets (VLAN 10, VLAN 20, 192.168.1.x). Kea DDNS auto-registers every DHCP client in Technitium (RFC 2136, A+PTR).

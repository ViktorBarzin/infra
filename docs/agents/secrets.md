# Secrets

## Secrets Management — Vault KV
- **Vault stack self-reads**: `data "vault_kv_secret_v2" "vault"` reads its own OIDC creds from `secret/vault`.
- **ESO (External Secrets Operator)**: `stacks/external-secrets/` — chart **2.12.0 / app v2.12.0** (migrated 0.12.1→2.6.0 on 2026-06-22, one minor at a time; 2.6.0→2.12.0 direct on 2026-10-10, since 2.7-2.12 changed no CRD versions; helm_release has `atomic=true` and `cleanup_on_fail=true`). **~104 ExternalSecrets across 73 files**, all on **API version `v1`** (migrated v1beta1→v1 on 2026-06-22 — there is NO v1beta1→v1 conversion webhook, so all CRs were rewritten to v1 on chart 0.16.2 before 0.17 removed v1beta1; see `docs/plans/2026-06-21-eso-0.12-to-2.x-migration-design.md`). Two ClusterSecretStores: `vault-kv` and `vault-database`. **refreshInterval is split by store on purpose (2026-09-03):** `vault-kv` ExternalSecrets refresh at `1h`, `vault-database` ones stay at `15m`. Every Vault database role here is a STATIC role rotating weekly, and the old password dies the instant it rotates, so the app is broken until ESO polls and Reloader restarts it — measured at 4-7 min of CI downtime per rotation for woodpecker at 15m (infra#45), which an hourly refresh would stretch toward 60. Since 2026-10-30 the `db-rotation-watcher` CronJob (`stacks/vault`) force-syncs `vault-database` ExternalSecrets seconds after each Tuesday rotation, but it runs only in that hour and the 15m poll is its fallback, so keep `vault-database` at 15m (runbook: `docs/runbooks/db-credential-rotation.md`). (1 pre-existing dead ES — `instagram-poster-secrets` — fails "cannot find secret data" on a missing Vault key, unrelated. `payslip-ingest-secrets` was in that state too and is **no longer**: verified `SecretSynced True` with all 6 keys on 2026-08-16, so re-check before citing an ES as dead.)
- **Plan-time pattern**: Former plan-time stacks use `data "kubernetes_secret"` to read ESO-created K8s Secrets at plan time (no Vault dependency). First-apply gotcha: must `terragrunt apply -target=kubernetes_manifest.external_secret` first, then full apply. `count` on resources using secret values fails — remove conditional counts.
- **14 hybrid stacks** still keep `data "vault_kv_secret_v2"` for plan-time needs (job commands, Helm templatefile, module inputs). Platform has 48 plan-time refs — no migration possible without restructuring modules.
- **Never pass a `data "vault_kv_secret_v2"` value into `templatefile()`** (Terraform 1.15 + vault provider v5). Provider v5 marks that data source deprecated, so its values carry sensitive + deprecation marks, and Terraform's plan-vs-apply consistency check on `templatefile()` hashes the marks: the apply then fails, intermittently, with `Call to function "templatefile" failed: function returned an inconsistent result` (plan passes). Hit grafana on 2026-10-17 (fix: `set_sensitive` on the helm_release) and prometheus 2026-11-02..08, infra#172 (fix: the template carries literal `@@NAME@@` placeholders and `replace()` fills them after rendering, for values buried in string fields where `set_sensitive` cannot reach). See the comments in `stacks/monitoring/modules/monitoring/{grafana,prometheus}.tf`.
- **Database rotation**: Vault DB engine rotates all 32 static roles weekly, each in a slot on Tuesday 10:00-10:45 UTC (table in `stacks/vault/main.tf`, "Static role rotation slots"), and the `db-rotation-watcher` CronJob pushes each rotation to its ExternalSecrets within seconds. MySQL roles rotate with `RETAIN CURRENT PASSWORD`, so the previous password stays valid until the next rotation. How it works, adding a role, and checking a Tuesday: `docs/runbooks/db-credential-rotation.md`. Excluded: authentik (PgBouncer), root users. **Apps that read a rotated secret only at startup** (env var / initContainer, not a hot-reloaded mount) MUST carry a Reloader annotation (`secret.reloader.stakater.com/reload: <secret>`) or they keep the stale password and silently fail DB auth on each rotation until manually restarted — matrix's Synapse `inject-db-password` initContainer hit exactly this (found via Loki 2026-06-05, ~12.9k auth-fail lines/hr); matrix has since migrated to tuwunel (RocksDB, no Postgres) on 2026-06-08 and is no longer in the rotation list above. **The alternative that avoids the restart entirely** (tv, then f1-stream, 2026-09-26): mount the ESO-generated Secret as a FILE, template it with `reloader.stakater.com/ignore: "true"` so a Deployment carrying `reloader.stakater.com/auto` does not roll on each rotation, and have the app read the password from the file for every new connection (asyncpg takes a password callable). The static role's Tuesday slot bounds the gap before the file refreshes, when new connections fail but pooled ones keep working. See `stacks/tv/main.tf` (`viewing_db_external_secret`) and the `pg-tv` static role in `stacks/vault/main.tf`. Technitium uses a password-sync CronJob (every 6h, and right after each rotation via the watcher's `rotation.viktorbarzin.me/after-sync-cronjobs` annotation) to push rotated password to the Technitium app config via API, disable SQLite + MySQL logging, check PG plugin is loaded, configure PG query logging (90-day retention), and disable SQLite on secondary/tertiary instances.
- **Cloud (`stacks/vault/cloud.tf`, policy text in `cloud_policies.tf`)**: Cloud's reconciler and its Projects never create Vault policies or auth roles. Everything is fixed here and tested by `tests/cloud-access.test.sh` against a dev Vault wired to a kind cluster. **`cloud-reconciler`** (Kubernetes auth, service account `cloud-reconciler` in namespace `cloud`, 1h tokens): create/read/update/delete on `secret/data/cloud/*` and `secret/metadata/cloud/*`, read-only on `secret/cloud/system`, and read on `database/static-creds/pg-cloud-provisioner` and `pg-cloud-state`. Nothing else, so its OpenTofu Vault provider must set `skip_child_token = true` (the policy has no `auth/token/create`). **`cloud-project`**: one templated policy, `read` on `secret/data/cloud/{{identity.entity.aliases.<kubernetes accessor>.metadata.service_account_namespace}}/*`, so a Project namespace's token reads only its own tree. Its auth role admits service account `cloud-secrets` in any namespace labelled `cloud.viktorbarzin.me/managed=true` (`bound_service_account_namespace_selector`, Vault 1.16+, live 2.2.0). Vault reads the namespace's labels at login with its own pod token, so the `vault` service account holds `get` on namespaces (ClusterRole `vault-namespace-reader`); without it every `cloud-project` login fails. Each Project uses a namespaced SecretStore with this role, never the `vault-kv` ClusterSecretStore, and an admission policy enforces that (`docs/agents/security.md`). **`secret/cloud/system`** is written only by `stacks/authentik/cloud-reconciler.tf`: `authentik_token` (the reconciler's Authentik API token) and `ghcr_pull_token`. The second is copied from `secret/viktor` key `cloud_ghcr_pull_token`, which Viktor seeds with a read:packages-only GitHub token (never the admin PAT); it stays empty until then. CI may write that one path (policy `ci`). Static roles `pg-cloud`, `pg-cloud-provisioner` and `pg-cloud-state` rotate in the Tuesday 10:17 slot. The rest of `secret/cloud/*` belongs to Cloud (AGENTS.md, "Cloud-owned objects").
- **K8s credentials**: Vault K8s secrets engine. Roles: `dashboard-admin`, `ci-deployer`, `openclaw`, `local-admin`. Use `vault write kubernetes/creds/ROLE kubernetes_namespace=NS`. Helper: `scripts/vault-kubeconfig`.
- **CI/CD (GHA + Woodpecker)**: Docker builds run on **GitHub Actions** (free on public repos). Woodpecker is **deploy-only** — receives image tag via API POST, runs `kubectl set image`. Woodpecker authenticates via K8s SA JWT → Vault K8s auth. Sync CronJob pushes `secret/ci/global` → Woodpecker API every 6h. Shell scripts in HCL heredocs: escape `$` → `$$`, `%{}` → `%%{}`.
- **Platform cannot depend on vault** (circular). Apply order: vault first, then platform. Platform has 48 vault refs, all in module inputs — no ESO migration possible.
- **Complex types** (maps/lists like `homepage_credentials`, `k8s_users`) stored as JSON strings in KV, decoded with `jsondecode()` in consuming stack `locals` blocks.
- **New stacks**: Add secret in Vault UI/CLI at `secret/<stack-name>`, add ExternalSecret + `data "kubernetes_secret"` for plan-time, `secret_key_ref` for env vars. Use `data "vault_kv_secret_v2"` only if `data "kubernetes_secret"` won't work (e.g., first-apply bootstrap).
- **Backup CronJob**: `vault-raft-backup` uses manually-created `vault-root-token` K8s Secret (independent of automation).
- **Bootstrap (fresh cluster)**: Comment out data source + OIDC → apply Helm → init+unseal → populate `secret/vault` → uncomment → re-apply.

## A secret never goes on a sudo command line
On the devvm, sudo writes its whole command line to `/var/log/auth.log` and the journal, which promtail ships to Loki (`{job="devvm-journal"}`, 26 weeks). That includes `ENV=VAR=value` for every `sudo VAR=value` **and for every variable named in `sudo --preserve-env=VAR`** (checked 2026-11-11: both forms log the value; `sudo -E` does not, but it hands root your `HOME`). wizard's admin Vault token reached Loki in 8 sudo lines between 2026-11-08 and 2026-11-11, one of them a `sudo grep <token>` check. That token (accessor `8FkS6c...`) was revoked on 2026-11-11 at 14:27 UTC and replaced by a new periodic `token-devvm-wizard`; the logged lines now hold a dead token. Read the secret from its file inside the root command, so the logged line holds only the path:
```sh
sudo VAULT_ADDR=https://vault.viktorbarzin.me bash -c 'VAULT_TOKEN="$(cat "/home/$SUDO_USER/.vault-token")" exec t3-provision-users'
```
The same goes for `sudo grep <secret> ...`: use `grep -F -f <file>`.

Since 2026-11-11 the devvm's promtail masks secret-shaped values before a line leaves the box (`*mask_secrets` in `scripts/devvm-promtail.yaml`, tested by `tests/devvm-promtail-redact.test.sh`): Vault, GitHub and AWS tokens, JWTs, private key blocks, `Authorization`/`Bearer` values, URL passwords, `curl -u`, `mysql -p`, and the values of secret-looking names (`ENV=VAULT_TOKEN=...`, `token=`, `"password": "..."`, `--token`). It is a net, not a licence: a bare password with no name or shape, or a token sudo splits across two `(command continued)` lines, still reaches Loki, so the rule above stands.

## Sealed Secrets (User-Managed Secrets)
For secrets that users manage themselves (no SOPS/git-crypt access needed):
1. **Create**: `kubectl create secret generic <name> --from-literal=key=value -n <ns> --dry-run=client -o yaml | kubeseal --controller-name sealed-secrets --controller-namespace sealed-secrets -o yaml > sealed-<name>.yaml`
2. **Commit**: Place `sealed-*.yaml` files in the stack directory (`stacks/<service>/`)
3. **Terraform picks them up** automatically via `fileset` + `for_each`:
   ```hcl
   resource "kubernetes_manifest" "sealed_secrets" {
     for_each = fileset(path.module, "sealed-*.yaml")
     manifest = yamldecode(file("${path.module}/${each.value}"))
   }
   ```
4. **Deploy**: Push → CI runs `terragrunt apply` → controller decrypts into real K8s Secrets
- Only the in-cluster controller has the private key. `kubeseal` uses the public key — safe to distribute.
- Naming convention: files MUST match `sealed-*.yaml` glob pattern.
- The `kubernetes_manifest` block is safe to add even with zero sealed-*.yaml files (empty for_each).

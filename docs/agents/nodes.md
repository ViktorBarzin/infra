# Node kubelet and OS disk tuning

Moved verbatim from the repo's agent instruction files (`AGENTS.md`, `.claude/CLAUDE.md`) on 2026-09-22, when the two merged into one root `AGENTS.md`. Related as-built docs: `docs/architecture/compute.md`.

## From the `.claude/CLAUDE.md` Instructions list

- **Node kubelet tuning — where each setting really comes from** (rewritten 2026-09-05, code-yypr; every source in the previous version of this bullet was wrong). **`playbooks/k8s-node-tuning.yml` is the only thing that sets any of these**, and `/var/lib/kubelet/config.yaml` is where it writes them. `stacks/infra/main.tf` manages none of them and never did — the old bullet named it as the template and quoted systemReserved=512Mi, kubeReserved=512Mi, evictionHard=500Mi, evictionSoft=1Gi as "current values" when live `/configz` on all six nodes reported the first three absent and evictionHard at the kubelet defaults. **Declared today, at the values the nodes actually run:** `allowedUnsafeSysctls` (`net.ipv4.ip_forward`), `shutdownGracePeriodByPodPriority` (the 9-rung ladder, code-xgcg), `shutdownGracePeriod`/`shutdownGracePeriodCriticalPods` (both `0s`, pinned because kubelet refuses to start if either is non-zero alongside the ladder), `memorySwap: LimitedSwap`, `serializeImagePulls: true`, `imageMaximumGCAge: 168h0m0s` (kubeadm's spelling of 168h; the drift check compares text), `imageGCHighThresholdPercent: 85` / `imageGCLowThresholdPercent: 80`, and `evictionHard` (memory.available 100Mi, nodefs.available 10%, nodefs.inodesFree 5%, imagefs.available 15%, imagefs.inodesFree 5%). **The last two blocks are the kubelet's own defaults, written down on purpose** — an undeclared default and an erased setting look identical from the repo, and that ambiguity is what let a plan nearly ship imageGC 70/60 as a "restoration" (code-fjtu). The cost is that an upstream default change is now something we have to notice rather than inherit. **NOT declared, and it is a decision not an oversight:** `systemReserved`, `kubeReserved` and `evictionSoft` — bead `code-eu6l`. Also absent: `maxParallelImagePulls` (retired), `containerLogMaxFiles`, `evictionPressureTransitionPeriod`. **Changing VM memory on a node changes nothing here today**, because no reservation scales with it; if code-eu6l lands, revisit that. **Verify with `scripts/check-node-kubelet-tune`**, which reads each kubelet's live `/configz` rather than the file on disk.
- **Node OS disk tuning**: the root filesystem mount options are declared in `playbooks/k8s-node-tuning.yml` as of 2026-09-13 and applied live with a remount. Every node mounts `/` with `errors=remount-ro,commit=60`. **They were declared nowhere before that**, only described in this bullet as coming from cloud-init, which `modules/create-template-vm/cloud_init.yaml` does not in fact set. Two nodes had drifted: node4 and node5 ran `discard,commit=30` while node1/node2/node3/master ran `errors=remount-ro,commit=60`, a difference nobody could see because the repo declared neither. **`discard` is deliberately absent**: `fstrim.timer` was enabled on all six, so the two drifted nodes were running continuous TRIM on top of a weekly batch job. Measured on node5 over 47.8 days, that was 16,541,765 discard operations covering 8,774 GB (183.5 GB/day) against exactly zero on node1; after the change node5 issued 0 discards in 60 s. **k8s-master has no weekly fstrim since 2026-10-19** (`playbooks/k8s-node-tuning.yml`, tag `fstrim`): each run stalled etcd for 5-12 minutes with WAL fsync p99 6.9-7.6 s (09-20, 10-04, 10-18) while the pve host was idle, and its LV is 100% allocated with 0 discards reaching the host, so the trim reclaimed nothing. The other five nodes keep the weekly timer. The regexp that edits fstab must use `[ \t]` and never `\s`, because `\s` matches a newline and a trailing `\s*$` swallowed the file's final newline on the four already-correct nodes. **Image GC runs at 85/80, which are the kubelet defaults and are now also declared** in `playbooks/k8s-node-tuning.yml` (2026-09-05, code-yypr) so that a change to them is a diff someone approves. Until then `imageGCHighThresholdPercent` and `imageGCLowThresholdPercent` were set nowhere in this repo while live configz on all six nodes read 85/80. An earlier version of this bullet claimed 70/60 sourced from `stacks/infra/main.tf`; that stack does not manage these keys and never did, so treat any change to them as new behaviour rather than a restoration. Lowering to 70 today would shed 40-60 GB of warm image cache on node2 (80.4%) and node5 (83.3%) the moment it applied. Corrected 2026-09-03, code-fjtu. **journald `Storage=volatile` (RAM, `RuntimeMaxUse=200M`) since 2026-06-30 (code-oflt)** — node+pod journals ship to Loki via alloy (`loki.source.journal`), so on-disk journald was pure write-IOPS overhead on the IOPS-bound `sdc`; moving it to RAM cut node5's OS-disk writes ~94% (`jbd2` 931→46 KB/s) and freed ~4 GB each on node4/node5 (which had drifted to uncapped persistent). Applied to running nodes via `qm guest exec` drop-in `/etc/systemd/journald.conf.d/90-oflt-volatile.conf` + journald restart. Trade-off: a hard crash loses the last unshipped journal (Loki has the rest).
- **Opportunistic workers (ADR-0045, `GLOSSARY.md`)**: a node with the label `node-role.viktorbarzin.me/opportunistic=true` and the taint `node-role.viktorbarzin.me/opportunistic=true:NoSchedule` (the first is `dell-worker`, London, over the WireGuard tunnel) is offline for days by design and nothing may depend on it. Everything that asks "are all nodes healthy" keys on that label, never on a node name: the kured sentinel gate (`stacks/kured`), the k8s upgrade chain (`stacks/k8s-version-upgrade`), check 1 of `scripts/cluster_healthcheck.sh`, the kubelet half of `k8s-node-drift-check` (`scripts/check-node-kubelet-tune`, skipped while the node is not Ready), and the node, DaemonSet and capacity alerts (`docs/agents/monitoring.md`). kured does not run there; the node is patched and upgraded by re-running `playbooks/physical-node.yml`. `tigera-operator` has a node affinity that keeps it off such nodes, because it tolerates every taint and would stay bound to an offline node. `dell-worker`'s pod MTU is 1280 through the FelixConfiguration `node.dell-worker` in `stacks/calico`. The tunnel's path is 1200 bytes, but IPv6 needs 1280 on the pod interface, so packets over 1150 bytes are fragmented in the tunnel. calico-node there finds its IPv6 address on the dummy interface `k8s-v6` (`calico_ipv6_address`, `playbooks/physical-node.yml`). A new workload that tolerates the taint must survive the node vanishing for days. The GPU Operator does not tolerate the taint yet, so `dell-worker`'s P2000 gets no device plugin: `daemonsets.tolerations` in `stacks/nvidia/modules/nvidia/values.yaml` also lands in the OnDelete driver DaemonSet on k8s-node1, which leaves the ClusterPolicy notReady until the T4 driver pod restarts (a GPU outage), so if an Opportunistic worker ever needs its GPU, add it together with a gpu-operator chart bump, whose driver roll happens anyway, along with a `node-feature-discovery.worker.tolerations` entry (NFD must label the node before the operator sees its GPU). Not planned: the Dell's Spill-over work is shelved (`docs/plans/2026-11-21-dell-opportunistic-worker-design.md`).
- **Security patching and cloud-init**: unattended-upgrades, its two `apt.conf.d` files and the `kubelet`/`kubeadm`/`kubectl`/`containerd.io` holds are declared in `playbooks/k8s-node-tuning.yml` (tags `patching`, `cloudinit`) since 2026-10-18, so the hourly drift check reports a node that loses them. It also writes a needrestart drop-in (node4/node5, the only nodes with needrestart) so the post-upgrade hook never restarts containerd or kubelet: per-package restarts during a backlog catch-up took node5 NotReady on 2026-10-18 (infra#128). The same play writes `/etc/cloud/cloud-init.disabled` on a joined node, because k8s-node5's hand-made bootstrap snippet re-ran on 2026-07-18 and 2026-07-28, uninstalled unattended-upgrades and left the node unpatched until 2026-10-18. The node4 and node5 snippets on the Proxmox host are now managed by `playbooks/pve-host.yml` (tag `snippets`). Runbook: `docs/runbooks/k8s-node-auto-upgrades.md`.

## Physical nodes

A Physical node is a Kubernetes node on its own hardware (ADR-0045, `GLOSSARY.md`). `playbooks/physical-node.yml` builds one from a fresh Ubuntu 26.04 install, for the inventory group `physical_nodes` with per-node settings in `playbooks/host_vars/<node>.yml`. The first is `dell-worker`, an Opportunistic worker in London with the taint `node-role.viktorbarzin.me/opportunistic=true:NoSchedule`.

- **State volume.** Cluster state and secrets live on a LUKS2 partition that Clevis unlocks from the node's own Tang (`stacks/tang`) after the network is up. `/etc/kubernetes`, `/var/lib/kubelet`, `/var/lib/containerd`, `/etc/cni/net.d`, `/var/lib/calico`, `/var/log/pods`, `/var/log/containers` and `/opt/actions-runner` are bind mounts from it. The recovery passphrase is in Vault `secret/tang-<node>`.
- **Tether.** A per-minute timer closes the volume after 10 minutes without Tang and reopens it when Tang answers.
- **Tuning.** The playbook ends by importing `k8s-node-tuning.yml` for the same host, so a Physical node gets the same kubelet, containerd and patching settings as the VM nodes. Two GRUB tasks there skip it (`physical_node=true`), because it boots by UEFI and has no QEMU disk. The hourly drift check covers `k8s_nodes` only.
- **GPU.** A card the GPU Operator's driver does not support keeps a host driver (`gpu_driver`) and the labels `nvidia.com/gpu.deploy.driver=false` and `nvidia.com/gpu.deploy.container-toolkit=false`.

How to add a node, test the Tether, rotate Tang keys and act after a theft: `docs/runbooks/physical-node.md`.

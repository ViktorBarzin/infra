# Node kubelet and OS disk tuning

Moved verbatim from the repo's agent instruction files (`AGENTS.md`, `.claude/CLAUDE.md`) on 2026-09-22, when the two merged into one root `AGENTS.md`. Related as-built docs: `docs/architecture/compute.md`.

## From the `.claude/CLAUDE.md` Instructions list

- **Node kubelet tuning — where each setting really comes from** (rewritten 2026-09-05, code-yypr; every source in the previous version of this bullet was wrong). **`playbooks/k8s-node-tuning.yml` is the only thing that sets any of these**, and `/var/lib/kubelet/config.yaml` is where it writes them. `stacks/infra/main.tf` manages none of them and never did — the old bullet named it as the template and quoted systemReserved=512Mi, kubeReserved=512Mi, evictionHard=500Mi, evictionSoft=1Gi as "current values" when live `/configz` on all six nodes reported the first three absent and evictionHard at the kubelet defaults. **Declared today, at the values the nodes actually run:** `allowedUnsafeSysctls` (`net.ipv4.ip_forward`), `shutdownGracePeriodByPodPriority` (the 9-rung ladder, code-xgcg), `shutdownGracePeriod`/`shutdownGracePeriodCriticalPods` (both `0s`, pinned because kubelet refuses to start if either is non-zero alongside the ladder), `memorySwap: LimitedSwap`, `serializeImagePulls: true`, `imageMaximumGCAge: 168h`, `imageGCHighThresholdPercent: 85` / `imageGCLowThresholdPercent: 80`, and `evictionHard` (memory.available 100Mi, nodefs.available 10%, nodefs.inodesFree 5%, imagefs.available 15%, imagefs.inodesFree 5%). **The last two blocks are the kubelet's own defaults, written down on purpose** — an undeclared default and an erased setting look identical from the repo, and that ambiguity is what let a plan nearly ship imageGC 70/60 as a "restoration" (code-fjtu). The cost is that an upstream default change is now something we have to notice rather than inherit. **NOT declared, and it is a decision not an oversight:** `systemReserved`, `kubeReserved` and `evictionSoft` — bead `code-eu6l`. Also absent: `maxParallelImagePulls` (retired), `containerLogMaxFiles`, `evictionPressureTransitionPeriod`. **Changing VM memory on a node changes nothing here today**, because no reservation scales with it; if code-eu6l lands, revisit that. **Verify with `scripts/check-node-kubelet-tune`**, which reads each kubelet's live `/configz` rather than the file on disk.
- **Node OS disk tuning**: the root filesystem mount options are declared in `playbooks/k8s-node-tuning.yml` as of 2026-09-13 and applied live with a remount. Every node mounts `/` with `errors=remount-ro,commit=60`. **They were declared nowhere before that**, only described in this bullet as coming from cloud-init, which `modules/create-template-vm/cloud_init.yaml` does not in fact set. Two nodes had drifted: node4 and node5 ran `discard,commit=30` while node1/node2/node3/master ran `errors=remount-ro,commit=60`, a difference nobody could see because the repo declared neither. **`discard` is deliberately absent**: `fstrim.timer` is enabled on all six, so the two drifted nodes were running continuous TRIM on top of a weekly batch job. Measured on node5 over 47.8 days, that was 16,541,765 discard operations covering 8,774 GB (183.5 GB/day) against exactly zero on node1; after the change node5 issued 0 discards in 60 s. The regexp that edits fstab must use `[ \t]` and never `\s`, because `\s` matches a newline and a trailing `\s*$` swallowed the file's final newline on the four already-correct nodes. **Image GC runs at 85/80, which are the kubelet defaults and are now also declared** in `playbooks/k8s-node-tuning.yml` (2026-09-05, code-yypr) so that a change to them is a diff someone approves. Until then `imageGCHighThresholdPercent` and `imageGCLowThresholdPercent` were set nowhere in this repo while live configz on all six nodes read 85/80. An earlier version of this bullet claimed 70/60 sourced from `stacks/infra/main.tf`; that stack does not manage these keys and never did, so treat any change to them as new behaviour rather than a restoration. Lowering to 70 today would shed 40-60 GB of warm image cache on node2 (80.4%) and node5 (83.3%) the moment it applied. Corrected 2026-09-03, code-fjtu. **journald `Storage=volatile` (RAM, `RuntimeMaxUse=200M`) since 2026-06-30 (code-oflt)** — node+pod journals ship to Loki via alloy (`loki.source.journal`), so on-disk journald was pure write-IOPS overhead on the IOPS-bound `sdc`; moving it to RAM cut node5's OS-disk writes ~94% (`jbd2` 931→46 KB/s) and freed ~4 GB each on node4/node5 (which had drifted to uncapped persistent). Applied to running nodes via `qm guest exec` drop-in `/etc/systemd/journald.conf.d/90-oflt-volatile.conf` + journald restart. Trade-off: a hard crash loses the last unshipped journal (Loki has the rest).

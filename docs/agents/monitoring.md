# Monitoring and alerting

Moved verbatim from the repo's agent instruction files (`AGENTS.md`, `.claude/CLAUDE.md`) on 2026-09-22, when the two merged into one root `AGENTS.md`. Related as-built docs: `docs/architecture/monitoring.md`.

## Monitoring & Alerting
- **Alert-on-change routing** (alert-noise-reduction 2026-06-12, `route` block in `prometheus_chart_values.tpl`): warning/info notify ONCE then stay quiet while firing (`repeat_interval: 8760h` ≈ off); criticals re-ping every 6h (was 1h); `send_resolved` on. Standing state is reviewed via the daily digest, not re-pings.
- **Daily alert digest**: CronJob `alert-digest` (monitoring ns, `alert_digest.tf` + `alert_digest.py`) posts the full current board grouped by severity + resolved-in-24h to `#alerts` at 08:00 Europe/London. Stock `python:3.12-alpine`, pure-stdlib (no pip/apk at runtime — avoids the status-page-pusher disk anti-pattern, id=559); reads Alertmanager v2 + Prometheus; reuses the Alertmanager Slack webhook via the `alert-digest` Secret. Safety net for alert-on-change.
- **Helm `pending-upgrade` auto-heal**: `helm-unstick` CronJob (monitoring ns, `helm_unstick.tf` + `helm_unstick.sh`, every 15m) clears Helm release records wedged in `pending-upgrade` — the recurring #6073 class where Woodpecker's cancel-on-new-push SIGKILLs `helm upgrade` mid-flight, blocking the release AND the later stacks in the same CI run. **Prevention**: `helm_release.prometheus` sets `wait = false` so helm no longer holds a ~15-min in-flight upgrade during the slow Recreate+WAL-replay roll (shrinks the SIGKILL window to ~2s). **Cure**: the CronJob deletes only a `pending-upgrade` secret that is >30m old (past any legit helm `--wait`) AND whose release still has a `deployed` fallback revision — non-disruptive (reverts the release pointer, live workload untouched, memory #6073). Scoped per-namespace (Roles, no cluster-wide secret access) to `{monitoring, crowdsec, nextcloud}`; `DRY_RUN` env safety-valve; a wedge with no deployed fallback is left for a human. **Detection**: cluster_healthcheck #18 (`helm list -a` flags `pending`). authentik/kyverno/metrics-server are deliberately out of scope (ancient one-offs, far more sensitive secrets) — clear a rare wedge there by hand. **Memory sizing matters and is not cosmetic (2026-08-08):** `kubectl get secret -l owner=helm` buffers every matched Secret in RAM before the jsonpath projection — the `monitoring` namespace alone holds 61 release records (~8.3 MiB gzipped) and kubectl peaks at ~**128 MiB** RSS. The original 96Mi limit memcg-OOM-killed kubectl on every run (~7-8 kills/run, ~610/day on whichever node the pod landed — visible only as `node_vmstat_oom_kill`, since cadvisor emitted no `container_oom_events_total` for it), and the script's `|| true` turned that into an empty result: **the job exited 0 and reported success while never inspecting a single release.** The limit went to 256Mi (2x measured peak) and the script **exits 1 when a namespace cannot be listed** instead of treating a failed query as "nothing wedged". That ceiling lasted 42 days. By 2026-09-19 `monitoring` held 152 release records, kubectl peaked at 219 MiB, and 12 of 96 daily runs were OOM-killed with an empty log, each raising `JobFailed` plus `CronJobFailingRepeatedly`. The limit is now **512Mi** (2x that peak, since 2d562dc2). Records grew about 2 a day (160 on 2026-09-23, 105 of them `prometheus` revisions) at roughly 1 MiB each. **Since 2026-09-23 all four monitoring releases (prometheus, grafana, alloy, loki) set `max_history = 10`**, which holds the namespace near 40 records. Helm prunes on each upgrade and never deletes the deployed revision that helm-unstick falls back to. crowdsec (24 records) and nextcloud (15) are uncapped and small. `--chunk-size` does not help, because `-o jsonpath` accumulates the whole list. A new helm release in a scanned namespace should carry the same cap.
- **Prometheus must not be Keel-managed (2026-08-16)**: `prometheus-server` carries `keel.sh/policy: never` as an ANNOTATION only (`server.deploymentAnnotations` in `prometheus_chart_values.tpl`) — that is what Keel reads and, since 2026-08-17, what the Kyverno exclude rule selects on. It briefly also carried a matching LABEL (`kubernetes_labels.prometheus_server_keel_optout`), removed 2026-08-17: see the Kyverno row for why a keel.sh/* label is drift. Terraform declares every image in this release, so a Keel bump is always reverted by the next apply and the two just take turns — Keel patch-bumped the `prometheus-backup` sidecar `docker.io/library/alpine:3.21` → `library/alpine:3.21.7` hourly (it also drops the registry prefix) and each flip replaced the pod: **11 ReplicaSets in 14h, deployment generation 242, and only 213 of an expected ~720 self-scrape samples in 24h** (the self-scrape job inherits `global.scrape_interval: 2m`, so 720 is the 24h ceiling — it was collecting under a third of the time). The visible symptom was alerting, not Prometheus: a restart clears in-memory alert state, so every `for:` timer restarts from zero — `DriftStacksMany` (`for: 30m`) re-fired and re-resolved all day (each Slack `[RESOLVED]` lands within ~2 min of a new ReplicaSet) and `DriftStackErrored` (`for: 2h`) could never stay up long enough to fire. **Any flapping alert with a long `for:` is worth checking against `kubectl get rs -n monitoring` before believing the alert's own subject.** Same fight `stacks/proxy` hit on its gluetun image the same day — see the Proxy row, which resolved it by digest-pinning instead.
- **Image-ownership conflicts (root-cause fix, 2026-08-16)**: two controllers can both be authoritative over `spec.template.spec.containers[*].image` — Keel versus a Terraform `helm_release`, a raw `kubernetes_deployment`, or an operator like the authentik server — and then they rewrite each other **forever**. The loop is **silent by construction**: Keel logs an ordinary `resource updated`, the other owner logs an ordinary reconcile, neither knows the other exists. Every instance was found via an unrelated downstream symptom, never directly: a flapping alert (`prometheus-server`, whose hourly restarts reset every alert `for:` timer), a dropped VPN tunnel (`proxy/proxy-gw-1`), a downgraded app (paperless-ngx to `:1.5.0`) — or **not at all**: `authentik/ak-outpost-public` sat at **generation 497** being downgraded 2026.2.6→2026.2.4 every ~4h with nobody aware. Measured 2026-08-16: **37 of 206** Keel-managed Deployments declared a second owner (28 `Helm`, 7 `terraform`, 2 `goauthentik.io`), and the same per-workload patch had been applied by hand **five separate times** (5 exporters, postiz, dbaas/mysql, proxy, prometheus). **TWO halves, both needed.** (a) PREVENT: Kyverno rule `keel-never-when-another-owner` (`keel-annotations.tf`) sets `keel.sh/policy=never` as an **annotation** on any workload whose `app.kubernetes.io/managed-by` is `Helm`/`terraform`/`goauthentik.io`. **Annotation only — never a label** (see the Kyverno row). It's a positive *set*, not an exclude, because Kyverno's add-only mutate **cannot remove** the `policy=patch` it already stamped (the `match-tag` removal needed a one-off kubectl sweep for exactly this) — so an exclude alone would leave all 37 still fighting. First-party apps are untouched: ghcr `:latest`/SHA images deployed by CI `kubectl set image` carry no `managed-by` label and keep auto-updating, so the 2026-05-17 enrollment expansion still stands. (b) DETECT: `image-flipflop-detect` CronJob (`image_flipflop.tf`, every 6h) flags a Deployment that produced ≥3 ReplicaSets in 24h **and put back an image set it had already replaced** — behaviour, not a label, so it also catches the residue `managed-by` undercounts (a raw `kubernetes_deployment` has no such label; only the `# KEEL_IGNORE_IMAGE` marker protects those). Alerts `ImageOwnershipConflict` + `ImageOwnershipDetectorStale`. **Distinguishing a fight from ordinary churn is the whole difficulty** — monotonic upgrade histories, repeated identical images, container reordering and single rollbacks must all stay quiet; that logic is unit-tested (`python3 image_flipflop_detect_test.py`, 14 cases) and was verified against live state (1,980 ReplicaSets → exactly the 3 known offenders, no false positives). **A RECENCY GUARD keeps it honest after a fix**: a finding needs its last *round* — the most recent moment an already-seen image came back — inside `ACTIVE_WITHIN_HOURS` (6h), so a fight that has been fixed clears within one scan instead of lingering the whole 24h window. Keyed on the last round, deliberately NOT on the newest ReplicaSet, or an ordinary deploy after the fight ended would revive the stale finding. Trade-off: a fight whose rounds are more than 6h apart can need a second scan to surface. Memory limit 192Mi is **measured** (~18 MiB JSON, ~75 MiB peak RSS), not guessed — see the helm-unstick row for why that matters.
- **Do we have stray pods? (2026-09-01)**: `stray-workload-detect` CronJob (monitoring ns, `stray_workload.tf`, daily 07:05) subtracts what Terraform DECLARES from what is actually RUNNING. Kyverno cannot answer this — it decides whether a pod is *allowed* (trusted registry, not privileged, no host namespaces, no CAP_SYS_ADMIN) and never whether anything *declares* it, so an object admitted correctly months ago that later drops out of `.tf` keeps passing every rule; the flow trail is no help either, since an undeclared workload nobody talks to leaves no edge. **The declared set is readable from a CronJob, which the design assumed it was not**: Tier-1 state lives in the `terraform_state` database on CNPG (root terragrunt.hcl `backend = "pg"`, one schema per stack, table `states`), so an init container projects all 162 schemas with one `\gexec` psql session (`stray_workload_extract.sql` — 328 declarations, 1.3s, 8.9 MiB peak psql RSS, measured; the jsonb work stays server-side). A dedicated read-only role `tf_state_reader` is created by an idempotent bootstrap Job (`stray_workload_db_init.sql`) rather than reusing `pg-terraform-state`, whose credential can WRITE state — state-write is arbitrary infra takeover on the next apply, a much bigger blast radius than the other secrets in that namespace. **`ON_ERROR_STOP=1` is load-bearing**: a schema the reader cannot SELECT must abort the extraction, because a SHORT inventory reads as a cluster full of strays. The six Tier-0 stacks are the one gap (local SOPS-encrypted state) — their 11 workloads are committed as `declared_tier0.json`, regenerated by `scripts/gen-tier0-workload-inventory.py`; forgetting produces a visible false positive, never a false negative, and the alert says which script to run. **Five accounting rules, in order**: exempt.json entry with a reason → name match → membership of a declared `helm_release` (a chart's Deployments are not in state, only the release is — 50 objects) → `ownerReference` (apiserver-maintained, so preferred over the self-asserted `managed-by` label, and it is what keeps every CronJob's Job pods quiet) → `app.kubernetes.io/managed-by` naming a reconciler we run (only `goauthentik.io`, whose server builds its outposts with no ownerReference). Bare pods get a 24h grace window plus a label exemption for services that start pods on demand (`app=proxy-browser`). **Two refusal guards** (the helm-unstick lesson, applied up front): under 150 declarations, or findings above 25% of the live set → push `stray_workload_inventory_ok 0`, report nothing, exit non-zero. Alerts `StrayWorkloadDetected` / `StrayWorkloadInventoryBroken` / `StrayWorkloadDetectorStale`. **Verified against live state 2026-09-01: 339 declarations vs 840 live objects, 3 findings, all real** — `servarr/qbittorrent-exporter` (live since 2026-03-25, keel-updated, in no state file, no `.tf` and no commit: a resource deleted from source without a destroy; it carries this repo's own `tier` label, which is why an ownership-label approach would have missed it), plus two Succeeded pods left behind by hand (`immich/sw-30953`, `monitoring/helm-unstick-manual`). 32 unit tests: `python3 stray_workload_detect_test.py`. Memory limits are MEASURED (psql 8.9 MiB peak → 64Mi; python 37.2 MiB peak over a 3.61 MiB `PartialObjectMetadataList` payload → 128Mi) — see the helm-unstick row for why that is not cosmetic.
- **Drift detection re-plans before it reports (2026-08-16)**: the nightly run's first pass finds drift candidates against a frozen checkout; a second pass re-plans **only those stacks against current master**, and a stack that comes back clean is counted clean. The cron also moved from `@daily` (00:00) to **`0 4 * * *`**, off `renew-tls-certificate` (`@weekly`, Sunday 00:00). Without this, a certificate renewal landing 5 minutes into the run made **79 of 92 changed resources the same `module.tls_secret`** (126 stacks manage it) and the report read as a mass revert. Errored stacks are deliberately NOT re-planned. Full detail: `docs/architecture/ci-cd.md` → "The confirmation pass".
- **Cascade inhibitions** (`inhibit_rules`): `NodeDown` AND `NodeConditionBad`/`NodeDiskPressure` suppress downstream pod-churn alerts (PodCrashLooping/PodImagePullBackOff/PodsStuckContainerCreating/ScrapeTargetDown/*ReplicasMismatch); `T3ProbeLegDown` suppresses `T3ProbeDropBurst` for the same `leg`; plus existing NFS/Traefik/Authentik/Power/Tuya/iDRAC cascades. No `equal` on the node rules (pod alerts carry no `node` label → cluster-wide, like NodeDown). **Planned-maintenance mute (2026-07-12):** `NodeMaintenanceInProgress` (info; any node cordoned ≥1m — kured drain-reboots and manual cordons alike) inhibits the whole reboot-blast list (NodeDown/TraefikDown/replica mismatches/OOM/RecentNodeReboot/…) so a routine kured reboot produces ONE Slack line instead of ~19; `NodeCordonedTooLong` (warning, 2h, deliberately uninhibited) guards forgotten cordons. Inhibition is Alertmanager-only — kured's alert gate and the sentinel gate read PROMETHEUS, so the `RecentNodeReboot` 1h settle window and alert-blocking still work unchanged. `PodStuckPending` (warning, 20m, scheduled-but-not-starting — FailedMount/attach-wedge/image-pull class) alerts the n8n-style failure as itself.
- **NodeDown needs the node-exporter down too (2026-09-26).** The `kubernetes-nodes` job reaches each kubelet through the apiserver proxy, so an apiserver restart used to make every node look down at once and page for whichever node stayed failed past 3m (k8s-node4, 2026-09-26 15:58). NodeDown now fires only while that node's node-exporter, scraped directly at the node IP, is not answering either. The rule uses `unless ... == 1`, so a node-exporter target that drops out of discovery still lets it fire. A dead kubelet on a live VM is covered by `NodeNotReady`, and the apiserver restart by `ControlPlaneStaticPodRestarted`. 30-day backtest: 38 episodes before, 11 after.
- **ScrapeTargetDown scrapes only Ready endpoints** (relabel `keep __meta_kubernetes_endpoint_ready=true` on both `kubernetes-service-endpoints` jobs) — completed CronJob pods lingering as NotReady EndpointSlice addresses no longer fire phantom "down" alerts (tts/tripit/beads, id=4895). Replaces the old "exclude completed CronJob pods" guidance; a Ready pod with a broken metrics endpoint still fires.
- Alertmanager is now scraped (`extraScrapeConfigs` job `alertmanager`) → `alertmanager_notifications_total`/`_alerts`/`_notifications_failed_total` available; it had no `prometheus.io/scrape` annotation so notification volume was previously unmeasurable.
- Every new service gets Prometheus scrape config + Uptime Kuma monitor. External monitors auto-created for Cloudflare-proxied services by `external-monitor-sync` CronJob (10min, uptime-kuma ns). Mechanism: `ingress_factory` auto-adds `uptime.viktorbarzin.me/external-monitor=true` whenever the ingress is publicly served (`dns_type` `"proxied"`/`"non-proxied"` — for proxied that means riding the `*` wildcard since ADR-0021, not a per-name record; `"internal"` and `"none"` get none — set `external_monitor = false` explicitly on internal-only ingresses so the sync's default opt-in doesn't re-add a doomed monitor; see `modules/kubernetes/ingress_factory/main.tf`) — no manual action needed on new services. The `cloudflare_proxied_names` list in `config.tfvars` is EMPTY since the 2026-07-09 wildcard consolidation (alertmanager/grafana/prometheus ride the wildcard); don't check that list when debugging "is this monitored?" questions.
- **External monitoring**: `[External] <service>` monitors in Uptime Kuma test full external path (DNS → Cloudflare → Tunnel → Traefik). Config: `stacks/uptime-kuma/`; targets discovered from the K8s ingress API (the `cloudflare_proxied_names` legacy fallback is empty since the 2026-07-09 wildcard consolidation; proxied hostnames resolve via the `*` wildcard, ADR-0021). NOTE: the `ExternalAccessDivergence` alert is DORMANT since 2026-05-26 — its `external_internal_divergence_count` metric was emitted by the disabled status-page pusher; genuine external-vantage coverage is gatus on mx2 (ADR-0020) + `StatusPageDown` + the egress probes.
- **Internal monitoring**: `internal-monitor-sync` (same stack) syncs two sources into Uptime Kuma every 10 min: the static `local.internal_monitors` list (databases, TCP ports, direct IPs) and any Service annotated `uptime.viktorbarzin.me/internal-monitor=true`, probed at `http://<svc>.<ns>.svc.cluster.local:<port><path>` and named `[Internal] <label>`. Optional companion annotations: `-name`, `-path` (default `/`; setting it also tightens accepted codes to 200-299), `-port` (default the port named http/web/api, else the first). Opt-IN, unlike the ingress side, and the orphan sweep only deletes `[Internal] `-prefixed monitors, never the static ones. Use it for services with no ingress, which `external-monitor-sync` cannot see.
- **An absence-detection Loki alert needs `or vector(0)` (2026-08-28)**: a `< N` threshold over `count_over_time` goes SILENT at exactly zero, the case it exists to catch — `sum()` returns *no series* when nothing matches, so the comparison yields an empty result and never fires. Only `> N` rules are safe without it (empty correctly means "nothing happened"), which is why this had not bitten before: `TerminalUpgradesCollapsed` is the FIRST `<` rule in `loki.tf`, against 41 `>` ones. Wrap as `(sum(count_over_time(...)) or vector(0)) < N`; verified live by pointing the same expression at a filter matching no lines. The guard also makes such a rule cover its log stream ceasing to ship at all — usually what you want, since "the thing is dead" and "its telemetry is dead" both need a look. `TerminalUpgradesCollapsed` itself watches ttyd WebSocket upgrades (`{job="devvm-journal",unit="ttyd.service"} |= "WS   /ws"`, one line per SUCCESSFUL attach) over 24h, `< 50` against a measured 227-259/day baseline, `for: 2h`, warning. It exists because terminal mode did not connect from any touch device for three days (25-28 Aug) while the collapse sat plainly visible in that stream and nothing watched it; the 24h window is deliberate (person-driven traffic makes an hourly threshold false-fire nightly) and it catches DEAD, not degraded — 25 Aug's 57 would not have fired because desktop still worked. Runbook `docs/runbooks/terminal-lobby-upgrades.md` carries the two-branch triage: ttyd down = ordinary service problem; ttyd UP = the page is dying before it opens a socket, so read the frontend's own `TLDIAG` exception telemetry. **Those TLDIAG records are JSON behind a `... TLDIAG ` line prefix with an `event.name` field** — the `| logfmt | name = "..."` queries in terminal-lobby's ADR-0008 predate the shipped shape and return nothing; strip the prefix with `line_format` then `| json`.
- **sdc disk I/O (rebuilt 2026-08-16)**: the shared 2x12 TB spindle now has seven rules in the `R730 Host` group. Two SYMPTOM alerts (`warning`): `HDDReadLatencyHigh` (>50 ms per read for 15m, guarded on >20 read IOPS so an idle device can't trip it — reads are what the PERC write-back cache cannot absorb, so this is the closest thing to a user-visible latency SLI here) and `HDDSaturated` (util >85%). Three RATE alerts (`info`): `HDDHighReadRate` (>90 MB/s), `HDDHighWriteRate` (>20 MB/s — **was 10 MB/s for 20m, which sat between p95 and p99 and never fired once in 30 days**, through the whole period sdc was the documented bottleneck), `HDDHighIOPS` (>1600). Two DAILY-VOLUME alerts (`info`): `HDDDailyWriteVolume` (>600 GB/24h) and `HDDDailyReadVolume` (>700 GB/24h) — these exist because every rate alert uses a 5m window with a 15m `for` and is therefore blind to a workload that reads or writes steadily all day without ever spiking, which is exactly how sdc reached 464 GB written / 606 GB read per day with nothing alerting. **Every threshold is anchored to a measured 7-day distribution at or just above p99** (written into the rule comments — re-derive rather than copy if the workload changes). All carry `keep_firing_for` so one busy stretch is one episode, and an inhibit rule stops the five volume alerts notifying while `HDDSaturated`/`HDDReadLatencyHigh` already describe the same event. `SSDHighWriteRate` (sdb >2 MB/s) is deliberately a **wear** canary, not a performance one: the 850 EVO is at ~28.5% of its rated TBW and idle, and 2 MB/s sustained is 173 GB/day. **Thresholds need a revisit once a full week of post-2026-08-16 data exists** — the write/read baselines were cut that day and the daily ones were set against the OLD baseline with headroom.
- Key alerts: OOMKill, pod replica mismatch, 4xx/5xx error rates, UPS battery, CPU temp, SSD writes, NFS responsiveness, ClusterCannotTolerateNonGpuNodeLoss (N-1 memory-request headroom — this is the real headroom alert; there is NO `ClusterMemoryRequestsHigh`; `ContainerNearOOM` (working_set/limit, added 2026-09-06) was REMOVED 2026-09-23 because it reported containers that were not killed and missed 3 of 4 that were (Postgres page cache counts as working set), so there is no pre-kill memory alert; `NodeLowFreeMemory` (MemAvailable < 4Gi for 10m), added alongside it, stays, and this alert's denominator now excludes the GPU node in BOTH halves; **both halves of its expression filter `kube_pod_status_phase{phase=~"Running|Pending"}` — kube-state-metrics keeps publishing `kube_pod_container_resource_requests` for Succeeded/Failed pods until the pod object is GC'd, and counting those phantom reservations made it flap for days (2026-08-08: k8s-node3 read 28.29 GiB vs 18.33 GiB genuinely running, ~10 GiB of finished CronJob pods) and drove a real 4Gi→3Gi cut to prometheus on 2026-07-26 chasing an unreal problem. Any new capacity / request-sum alert needs the same phase filter**), ContainerOOMKilled, PodStuckPending, ImmichSmartSearchSlow (context-search latency / clip_index cache eviction), AuthentikRootRouter5xxHigh (all-3-server-pods-NotReady cascade → 502/503/504 on the authentik `/` router). **The Traefik scrape keeps `traefik_router_requests_total`** (per-router `code` label) — the drop-regex in the `traefik` scrape job never touched the request counter, so per-router 429/5xx is queryable + alertable. It also **keeps `traefik_service_request_duration_seconds_bucket`** (2026-08-15): `IngressTTFBHigh`/`Critical` are a **p95 over 30m**, not a mean over 5m. The mean was decided by a single request on services taking a few requests a minute — 81 firings in the 7 days to 2026-08-15, none of them a service that was actually slow (matrix: 2ms baseline, single spikes to 4.5s, 0.09 req/s, and criticals re-ping every 6h). Keeping just the service histogram costs ~1.3k series (~1.4% of head); the router/entrypoint buckets stay dropped, as those are the ~5k/pod cardinality driver. **A mean over a low-traffic service is not a latency signal — use the p95**, and note `protocol!="websocket"` is load-bearing (authentik's outpost websockets average ~126s, terminal's ~28s, entirely by design).

Slug extraction is ANCHORED to the JSON key `"RequestPath":"` and requires 2xx/304 (read from `DownstreamStatus`) — UA/Referer are attacker-controlled; never extract metric labels from unanchored traefik-line regexes. The JSON anchor is stronger than the CLF byte position it replaced: Traefik escapes `"` as `\"` inside every value, so `"RequestPath":"` cannot appear inside a header value and `[^"]*` cannot cross out of one field. **`&` arrives HTML-escaped as `\u0026`** — a `?slug=` regex matching only a bare `&` silently returns zero, which is the trap in this port. Ported in the same commit: the two recording rules, `share_link_geo.py`, and `stacks/immich/download_truncation_detect.py`. Details: `docs/architecture/monitoring.md` → Share-link analytics row. **Loki chart GOTCHA (found 2026-07-06): ruler config key is `loki.rulerConfig` — `loki.ruler` is silently ignored**; it had been wrong since install, so NO Loki-ruler alert was delivered to Alertmanager until the rename (chart now pinned 7.0.0). - **Do Immich downloads actually finish? (2026-08-30)**: `immich-download-truncation` CronJob (immich ns, `stacks/immich/download_truncation.tf`, hourly at `:07`) joins Traefik access logs from Loki against `asset_exif.fileSizeInByte`. It exists because **a truncated download is logged as an ordinary success** — Traefik writes `200` + `Content-Length` before the body, so status code alone can never distinguish "delivered" from "connection died half way", and only the byte comparison can. **Two metrics, and conflating them is the trap:** `immich_original_downloads_cut` = a response carried fewer bytes than the file (ROUTINE on mobile — HTTP Range recovers it; in the session that prompted this, 5 of 9 assets were cut and 4 resumed byte-exact — **do not alert on this**, it fires for anyone on a train) versus `immich_original_downloads_unrecovered` = the range requests never covered the missing tail, so somebody holds a partial file.
